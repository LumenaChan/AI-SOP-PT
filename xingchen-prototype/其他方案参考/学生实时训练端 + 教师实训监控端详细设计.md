# 学生实时训练端 + 教师实训监控端详细设计

**版本：V1.0**  
**所属产品：AI 实训智能指导与考评平台**  
**模块定位：面向学生训练过程与教师课堂管理的核心前台应用**

---

# 一、设计目标

这一层产品不能简单理解成：

> 左边放摄像头视频，右边显示 AI 识别结果。

真正需要解决两个完全不同的问题。

对于学生：

> 我现在应该做什么？  
> 我刚才哪里做错了？  
> 我应该如何改正？  
> 我完成以后下一步是什么？

对于教师：

> 全班几十个学生谁需要我关注？  
> 哪个工位发生了严重问题？  
> 是学生操作错了，还是 AI 判断不确定？  
> 我什么时候需要介入？  
> 哪些问题正在全班集中发生？

所以学生端和教师端虽然共享同一套 Runtime Session，但交互目标完全不同。

---

# 二、核心设计原则

学生端核心原则是：

> **减少认知负担。**

不要向学生展示：

```text
Event Code
模型版本
Confidence
Runtime State
```

学生只需要理解教学语言。

教师端核心原则是：

> **管理注意力。**

老师不可能同时盯 24 个甚至 40 个实时视频。

AI 的核心价值之一就是：

> 把异常学生自动筛出来，让教师优先关注真正需要帮助的工位。

---

# 三、学生训练端与教师监控端关系

整体关系：

```text
          SOP Runtime Session
                   │
        ┌──────────┴──────────┐
        │                     │
    学生训练端             教师监控端
        │                     │
 当前步骤 / 提示        班级 / 工位 / 异常
 标准操作              实时进度
 错误纠偏              教师介入
 完成反馈              人工确认
        │                     │
        └──────────┬──────────┘
                   │
              训练结束
                   │
        ┌──────────┴──────────┐
        │                     │
     学生报告              教师复盘
```

---

# 四、学生训练端定位

学生训练端不是一个完整 LMS。

一期只服务：

> 学生正在进行的一次真实实训。

因此不要塞入：

课程社区、知识问答、学习资料库、消息中心等大量外围功能。

核心任务就是：

```text
进入训练
↓
准备检查
↓
执行SOP
↓
接受指导
↓
纠正错误
↓
完成训练
↓
查看复盘
```

---

# 五、学生端页面结构

一期建议学生侧只保留四个核心页面：

```text
我的实训
训练准备
实时训练
训练结果
```

考试模式可以复用同一套页面框架，但隐藏指导内容。

# 六、“我的实训”页面

学生登录后首页优先展示：

```text
待完成
进行中
已完成
```

实训卡片至少包含：

```text
实训名称
课程
教师
训练/考试模式
开始时间
截止时间
状态
```

例如：

```text
机械零部件标准装配

机械装配技术
张老师

训练模式

今天 14:00

状态：
待开始

```

# 七、进入训练前必须绑定工位

学生不能只是：

> 点击开始。

系统需要知道：

```text
谁
在哪个工位
使用哪个摄像头
进行哪个Session
```

因此启动训练时形成：

```text
Student
+
Station
+
SOP Version
+
Task
=
Runtime Session
```

---

# 八、工位绑定方式

一期建议支持最简单方式：

### 教师预分配

例如：

```text
张三 → 工位03
李四 → 工位04
```

学生登录以后自动识别。

也可以支持：

### 工位码绑定

每个工位显示二维码。

学生扫码或输入工位编号。

一期如果主要跑 PC 原型，优先做：

> 教师预分配 + 学生确认。

---

# 九、训练准备页面

正式启动 AI 判断前，必须增加：

> 环境准备检查。

页面展示：

```text
学生：张三
工位：03
训练：减速器拆装
```

下面：

```text
✓ 摄像头在线
✓ AI服务正常
✓ 工位绑定成功
✓ 学生身份确认
✓ 训练资源加载完成
```

如果需要 PPE：

```text
⚠ 尚未检测到防护眼镜
```

---

# 十、为什么需要训练准备

不能学生一点击进入：

> AI直接开始计时。

否则会把：

```text
整理工具
调整设备
老师讲解
```

全部当成 SOP 操作。

所以建议：

```text
准备阶段
↓
学生点击“开始训练”
↓
Session正式RUNNING
```

# 十一、学生实时训练页面总体布局

一期推荐：

```text
┌─────────────────────────────────────────┐
│ 减速器拆装             第 4 / 11 步     │
│ 已用时 03:28                         │
├─────────────────────┬───────────────────┤
│                     │ 当前步骤          │
│                     │                   │
│      实时视频        │ 拆除端盖螺栓     │
│                     │                   │
│                     │ 操作要求……        │
│                     │                   │
│                     │ [查看标准操作]    │
├─────────────────────┴───────────────────┤
│ 当前状态：操作中                         │
│                                         │
│ ✓ 工具正确                               │
│ ⚠ 请按照规定顺序操作                     │
└─────────────────────────────────────────┘
```

# 十二、视频是否必须一直展示

建议一期展示。

因为 PoC 阶段用户会天然关注：

> AI到底看到了什么。

而且便于教师和开发验证。

但长期学生端视频不一定需要占页面 50%。

后期可以允许：

```text
教学内容优先
视频缩小
```

一期原型阶段保持较大视频窗口即可。

---

# 十三、视频上的 AI 标注要克制

PoC 可以展示：

```text
人物框
工具框
ROI
```

但正式教学模式下不建议把全部算法框展示给学生。

因为：

```text
bbox
track id
confidence
```

都会产生视觉干扰。

建议支持两种显示方式。

### 教学模式

只显示必要视觉提示。

例如：

> 当前识别工具：扭矩扳手。

### 调试模式

显示完整检测框。

供实施人员使用。

---

# 十四、当前步骤卡片

学生训练时最重要的信息应该是：

```text
步骤编号
步骤名称
操作要求
标准图片/视频
注意事项
```

例如：

```text
第4步 / 共11步

拆除端盖螺栓

操作要求：
使用指定工具，按照对角顺序依次拆除端盖螺栓。

注意：
拆卸过程中保持端盖稳定。
```

---

# 十五、不要一次展示整套 SOP

训练模式默认只强调：

> 当前步骤。

学生可以查看：

```text
流程概览
```

但不要让整个屏幕一直显示：

```text
S01
S02
S03
……
S20
```

否则会增加注意力负担。

---

# 十六、流程概览

可以设计一个收起的步骤进度条：

```text
01 ✓
02 ✓
03 ✓
04 ●
05
06
07
……
```

状态：

```text
✓ 已完成
● 当前步骤
○ 待执行
⚠ 已发生异常
```

学生点击已完成步骤：

> 可以查看，但训练过程中不能随意修改状态。

---

# 十七、标准操作内容

学生可以点击：

> 查看标准操作。

弹出：

```text
标准图片
标准视频
操作说明
注意事项
```

标准视频最好只播放当前 Step 对应片段。

不要每次播放完整 SOP。

---

# 十八、标准视频查看会不会影响计时

训练模式建议：

> 查看标准操作时训练计时继续。

因为学生查看提示本身就是训练的一部分。

但系统需要记录：

```text
viewedStandardContent = true
```

以及：

```text
viewCount
```

以后可以用于：

> 学生辅助依赖度。

---

# 十九、系统提示的三种等级

学生端建议统一提示等级：

```text
信息
警告
严重
```

对应视觉语义。

### 信息

例如：

> 当前步骤已完成。

### 警告

例如：

> 当前工具选择不符合要求。

### 严重

例如：

> 检测到安全违规，请立即停止当前操作。

---

# 二十、普通正确反馈不要太频繁

如果学生每做一个小动作，系统都：

> 正确。  
> 正确。  
> 正确。

会非常干扰实训。

建议只在：

```text
步骤完成
关键节点完成
```

时给明显正反馈。

其余检测结果保持轻量。

---

# 二十一、步骤完成反馈

步骤完成以后：

```text
✓ 第4步已完成
```

短暂提示后自动切换：

```text
第5步
```

建议延迟：

> 0.5～1 秒左右。

让学生知道系统已经识别成功。

---

# 二十二、错误提示必须说明“发生了什么”

不要只显示：

> 操作错误。

建议：

```text
工具选择错误
```

或者：

```text
操作顺序不符合要求
```

这属于 Feedback Level 2。

---

# 二十三、是否直接告诉学生正确答案

一期建议训练模式默认使用较直接的指导：

```text
当前工具不符合要求，请使用扭矩扳手。
```

因为 MVP 首要验证：

> AI是否真正能帮助学生训练。

后期再做难度策略：

```text
基础训练
→ 直接提示

强化训练
→ 只告诉错误类型

模拟考试
→ 不提示
```

---

# 二十四、训练模式的错误恢复

例如：

```text
学生拿错开口扳手
↓
系统提示
↓
学生放回
↓
重新拿扭矩扳手
```

页面应该明确从：

```text
⚠ 工具错误
```

恢复：

```text
✓ 工具正确，请继续操作
```

不能错误提示一直挂在那里。

---

# 二十五、历史错误仍然保留

虽然实时提示已经恢复，但本次训练结果中仍然记录：

```text
工具选择错误 ×1
```

也就是说：

> 页面状态恢复正常 ≠ 历史错误消失。

---

# 二十六、错误提示不要阻塞操作

普通异常：

```text
WRONG_TOOL
OUT_OF_ORDER
TIMEOUT
```

建议采用页面内提示。

不要每次弹 Modal，要求：

> 点击确认才能继续。

这会严重破坏实际操作流。

---

# 二十七、只有严重事件才阻塞

例如：

```text
CRITICAL SAFETY
```

可以使用全屏红色警告：

> 检测到严重安全风险，请立即停止操作并等待教师处理。

同时通知教师端。

---

# 二十八、AI 不确定的学生提示

训练模式下，如果系统无法可靠判断：

不要显示：

> AI Confidence 0.63。

建议：

> 当前操作未能准确识别，请重新执行一次。

如果连续多次无法识别：

> 已通知教师协助确认。

---

# 二十九、不要无限要求学生重做

例如连续：

```text
3次 AI_UNCERTAIN
```

应该升级：

```text
需要教师确认
```

否则学生可能已经做对，只是 AI 一直识别不到。

建议步骤配置一个：

```text
maxRecognitionRetry
```

一期可以固定：

> 2～3 次。

---

# 三十、请求教师帮助

学生端建议提供：

> 请求教师帮助

按钮。

点击后：

```text
Teacher Assistance Request
```

教师驾驶舱将该工位提升优先级。

状态：

```text
请求帮助
```

---

# 三十一、为什么这个功能重要

AI 不能替代课堂中的教师。

系统更合理的角色是：

> 把大量常规观察自动化，把真正复杂的问题转给教师。

因此：

```text
AI自行解决
↓
AI不确定
↓
学生请求帮助
↓
教师介入
```

必须是一条完整链路。

---

# 三十二、教师介入后学生端状态

例如：

```text
老师正在查看你的工位
```

教师确认：

> 当前步骤已完成。

学生端：

```text
✓ 教师已确认本步骤完成
```

然后继续下一步。

---

# 三十三、暂停训练

训练场景建议学生不能随意暂停。

避免学生为了规避超时：

> 一直暂停。

权限建议：

```text
教师可暂停
学生可申请暂停
```

PoC 阶段可以简化为：

> 教师端暂停。

---

# 三十四、学生主动结束训练

学生点击：

> 结束训练

需要二次确认：

```text
当前还有3个步骤未完成。

确认结束后，未完成的必做步骤将被记录。

[继续训练]
[确认结束]
```

避免误操作。

---

# 三十五、训练完成页

Session 完成后先展示简单结果：

```text
训练完成

成绩：86
用时：08:42
完成步骤：11 / 12
异常：3
提示次数：4
```

主要按钮：

```text
查看训练报告
重新训练
返回
```

---

# 三十六、重新训练必须新建 Session

不能：

> 把当前 Session 重置。

应创建新的训练记录。

这样才能形成训练成长轨迹。

---

# 三十七、考试模式学生端

考试模式复用整体框架，但明显减少信息。

例如：

```text
考试：减速器拆装

剩余时间：18:32

[实时视频]

考试进行中
```

不显示：

```text
当前正确步骤
标准视频
错误提示
步骤是否完成
AI评分
```

---

# 三十八、考试模式是否显示步骤列表

这要根据学校考试规则。

一期建议 SOP/任务配置：

```text
showStepListInExam
```

默认：

> 显示考试项目要求，但不显示实时完成状态。

这样既支持：

> 有操作流程说明的考试，

也支持：

> 完全自主完成。

---

# 三十九、考试模式 AI 仍然完整运行

虽然学生看不到反馈，但后台照样记录：

```text
Step State
Exception
Time
Evidence
```

教师端是否实时看到错误，可以再配置。

---

# 四十、考试模式不建议老师随意介入

正式考试场景下：

> 教师介入会影响公平性。

所以教师监控端在考试模式中应减少：

```text
确认完成
重置步骤
```

等操作。

仅保留：

```text
系统异常处理
安全处理
终止考试
```

普通复核放到考试结束之后。

---

# 四十一、教师实训监控端定位

教师监控端不是：

> 24 路监控录像墙。

如果最终做成 CCTV 页面，AI价值几乎没有体现。

核心应该是：

> **AI驱动的课堂异常管理台。**

# 四十四、优先关注区域

这是教师端最重要的区域。

排序建议：

```text
CRITICAL安全异常
↓
学生请求帮助
↓
AI无法判断
↓
高等级异常
↓
长时间停滞
↓
普通异常
```

老师一进入页面就知道：

> 先去看谁。

# 四十五、工位卡片

每个工位不建议展示完整视频。

卡片只显示：

```text
工位号
学生
当前步骤
进度
状态
最近异常
```

例如：

```text
工位08
张三

第 7 / 12 步
紧固螺栓

⚠ 工具选择错误
持续 12 秒
```

---

# 四十六、正常工位卡片

例如：

```text
工位03
李四

第 8 / 12 步

正常
```

正常工位视觉权重应明显低于异常工位。

避免教师被大量正常状态干扰。

# 四十七、工位状态

教师端建议统一为：

```text

AI待确认
严重异常
暂停
已完成

```

不要直接展示 Runtime 内部状态。

# 四十九、教师训练模式下可执行操作

建议：

```text
确认当前操作正常
确认当前步骤完成
让学生重做当前步骤
暂停该工位
终止训练
发送提示
```

其中高频操作不要太多。

核心优先：

```text
确认
重做
提示
```

---

# 五十、教师人工确认

如果 AI 不确定：

```text
当前操作是否完成？

[确认已完成]
[确认未完成]
[继续观察]
```

教师点击后生成 Manual Event。

状态机继续运行。

---

# 五十一、教师“确认正常”与“确认完成”不同

例如 AI 报：

> WRONG_TOOL。

老师看到其实工具正确。

应点击：

> AI判断错误，当前操作正常。

这是：

```text
Dismiss Exception
```

而不是：

> 直接完成步骤。

否则会跳过后续完成条件。

---

# 五十二、教师发送提示

训练模式下教师可以向某工位发送：

```text
请检查工具选择
注意操作顺序
请查看标准视频
自定义文字
```

一期建议预设快捷提示。

不必做复杂聊天系统。

---

# 五十三、全班广播

教师可发送：

```text
全体暂停
继续训练
统一提示
```

例如：

> 请所有同学暂停操作，注意第 5 步操作要求。

这个功能很符合真实课堂。

---

# 五十四、全班暂停

教师点击：

> 全班暂停

所有运行 Session：

```text
RUNNING → PAUSED
```

计时停止。

恢复后继续。

这比逐个工位暂停实用得多。

---

# 五十五、异常聚合

如果短时间内多个学生出现同一个异常：

例如：

```text
8名学生
在 S07
发生 WRONG_TOOL
```

教师端应该自动聚合：

> 8 名学生在“步骤7 工具选择”出现相同问题。

这可能说明：

> 不是八个人都笨，而是教学设计或工具摆放存在问题。

---

# 五十六、课堂共性问题

页面可以显示：

```text
当前共性问题

S07 工具选择错误       8人
S04 操作顺序错误       5人
S09 操作超时           4人
```

教师点击即可看到涉及学生。

这会是一个很有价值的产品能力。

---

# 五十七、实时步骤分布

教师可以看到：

```text
S01   0人
S02   2人
S03   4人
S04   8人
S05   7人
S06   3人
已完成 6人
```

这样可以判断：

> 班级整体训练进度。

---

# 五十八、为什么步骤分布有价值

老师可以看到：

> 大部分学生都堵在 S04。

这可能说明：

```text
S04难度高
教学讲解不足
AI识别有问题
设备使用存在障碍
```

比只看总完成率更有帮助。

---

# 五十九、长时间停滞检测

系统可以定义：

```text
当前Step IN_PROGRESS
超过某个时间阈值
```

但还没有明确 Timeout。

教师端可以显示：

> 长时间停滞。

例如：

```text
工位12
S05
已持续 2分18秒
```

提醒教师主动查看。

---

# 六十、停滞不是学生异常

这里要区别：

```text
教学关注事件
```

和：

```text
正式评分异常
```

“停滞”可以只是教师提醒。

不一定扣分。

---

# 六十一、教师驾驶舱不要充斥模型指标

不显示：

```text
Precision
Recall
Confidence distribution
```

除非打开：

> AI详情。

教师核心关注：

```text
谁
在哪一步
出了什么问题
需要我做什么
```

---

# 六十二、AI置信度什么时候展示给老师

只有：

```text
AI不确定
```

或者教师进入复核/详细分析时展示。

例如：

```text
AI判断置信度：72%
```

平时没有必要。

---

# 六十三、设备异常必须明显区分

例如：

```text
🔧 工位16
摄像头离线
```

不能显示成：

> 学生异常。

教师点击看到：

```text
设备问题
不是学生操作问题
```

并提示：

> 当前 AI 判定已暂停。

---

# 六十四、设备异常优先处理逻辑

如果：

```text
摄像头离线
```

则该工位所有基于视觉的步骤判定：

```text
暂停
```

教师端需要明确：

> AI考评暂不可用。

不能继续显示正常训练。

---

# 六十五、教师视频查看

点击工位可以打开：

> 实时视频。

但首页默认不全部加载 30 路高清流。

技术上和产品上都没有必要。

可以使用：

```text
状态卡片
+
必要时按需打开视频
```

---

# 六十六、教师同时查看多个异常视频

一期可以允许最多：

> 2～4 个工位。

例如：

```text
异常对比视图
```

但不是核心 MVP。

先做单工位详情即可。

---

# 六十七、课堂结束

教师可以：

> 结束本次实训。

系统提示：

```text
仍有6名学生未完成。

其中：
3人正在训练
2人暂停
1人设备异常
```

选择：

```text
继续等待
结束全部训练
```

---

# 六十八、教师强制结束

被强制结束的学生 Session：

```text
TERMINATED
```

但终止原因必须记录：

```text
教师结束课堂
```

不要被判定成：

> 学生主动放弃。

---

# 六十九、训练结束后的课堂总结

任务结束后教师自动进入：

> 本次实训总结。

首先展示：

```text
参加 30
完成 28
未完成 2
平均成绩 82.4
平均用时 09:18
```

---

# 七十、课堂总结最重要的不是成绩分布

优先展示：

```text
高频异常
困难步骤
教师介入
AI待复核
```

例如：

```text
高频异常

1. S07 工具选择错误    40%
2. S10 漏复检          33%
3. S04 操作超时        27%
```

---

# 七十一、困难步骤

根据：

```text
错误率
平均耗时
重试次数
教师求助次数
```

可以形成：

```text
S07
综合困难度较高
```

一期不需要计算一个复杂“困难度分数”。

直接展示原始指标。

---

# 七十二、教师介入统计

例如：

```text
教师人工确认 12 次
学生请求帮助 8 次
全班提示 1 次
```

这对评价 AI 实际减负效果很重要。

---

# 七十三、AI减负不能只看自动评分率

还可以看：

```text
教师实际需要介入的工位比例
```

例如：

```text
30名学生
24人全程无需教师介入
6人需要介入
```

这个指标非常适合后期作为产品效果指标。

---

# 七十四、教师介入率

定义：

```text
发生人工干预的Session
/
全部Session
```

例如：

```text
6 / 30
= 20%
```

随着系统成熟：

> 希望常规训练中的人工介入率逐步降低。

---

# 七十五、教师关注时长

以后甚至可以统计：

> 教师在哪些步骤花时间最多。

但一期不必做。

先有：

```text
教师介入次数
```

即可。

---

# 七十六、学生帮助请求统计

学生频繁请求帮助也可以反映：

```text
SOP设计问题
教学难点
AI提示不够清楚
```

所以不要把：

> 请求帮助

当作纯消息功能。

它本身是教学行为数据。

---

# 七十七、学生端实时反馈记录

系统应保存：

```text
FeedbackRecord
```

例如：

```json
{
  "studentId": "student_01",
  "stepId": "S07",
  "type": "WRONG_TOOL",
  "message": "当前工具不符合要求，请重新选择。",
  "shownAt": "10:22:18"
}
```

用于后续判断：

> 学生是否依赖系统提示。

---

# 七十八、学生看过几次标准视频

同样保存：

```text
StandardMediaView
```

例如：

```text
S07
标准视频查看 3 次
```

以后可以形成：

> 哪些步骤学生最依赖标准示范。

---

# 七十九、训练中的“学习数据”和“考评数据”要分开

学习数据包括：

```text
提示次数
视频查看次数
重试次数
求助次数
```

考评数据包括：

```text
步骤结果
异常
成绩
```

不能全部混成“错误”。

---

# 八十、训练过程中的学生状态

教师端可以逐渐形成：

```text
顺利
频繁纠错
频繁求助
长时间停滞
AI识别困难
```

这些属于：

> 课堂管理状态。

不直接进入成绩。

---

# 八十一、不要一期自动给学生贴“能力差”标签

例如：

> 学习困难学生。

不建议。

一期只展示事实：

```text
请求帮助 4 次
S07 重试 3 次
本次用时高于班级平均
```

由教师自己判断。

---

# 八十二、考试教师监控端

考试模式监控首页依然展示：

```text
未开始
考试中
已交卷
设备异常
安全异常
```

但普通操作异常是否展示，需要配置。

一期建议：

> 教师可以看到异常数量，但不主动干预。

---

# 八十三、考试安全异常必须实时展示

即使考试模式静默：

```text
CRITICAL SAFETY
```

仍然必须立即推给监考教师。

因为安全优先于考试流程。

---

# 八十四、考试设备异常

例如摄像头掉线。

监考页面必须立即：

> 工位12 摄像头离线，AI评定已暂停。

并记录：

```text
system incident
```

供考试后决定：

> 是否需要补考或人工复核。

---

# 八十五、考试提交

学生点击：

> 提交考试。

弹出：

```text
确认提交考试？

提交后无法继续操作。

[返回]
[确认提交]
```

之后：

```text
Session Finalization
```

执行漏步、异常等最终确认。

---

# 八十六、考试结束后学生不要立即看到最终成绩

如果存在教师复核：

建议显示：

```text
考试已提交

成绩正在确认中。
```

直到：

```text
Assessment FINALIZED
```

再开放查看。

---

# 八十七、训练模式可以即时看报告

因为训练的价值就是即时反馈。

所以：

```text
Session COMPLETED
↓
立即生成训练报告
```

不必等教师确认所有普通异常。

但如果存在：

```text
REVIEW_REQUIRED
```

可以标记：

> 部分结果待教师确认。

---

# 八十八、任务模式配置

教师创建任务时建议选择：

```text
训练模式
考试模式
```

训练模式继续配置：

```text
是否允许查看标准视频
是否显示错误类型
是否直接提示正确操作
是否允许学生请求帮助
```

一期可以提供默认模板。

---

# 八十九、训练难度模板

为了避免教师配置太多参数，可以预设：

### 引导训练

```text
显示当前步骤
允许标准视频
详细错误提示
允许重复
```

### 自主训练

```text
显示当前步骤
标准视频可选
只提示错误类型
```

### 模拟考试

```text
不提示错误
不显示步骤完成状态
```

一期做两个模式也足够。

但产品结构上可以预留这一方向。

---

# 九十、实时训练端的空状态

如果 AI 尚未开始识别：

不要空白。

显示：

```text
等待开始训练
```

或者：

```text
请按照当前步骤开始操作，系统将自动识别。
```

---

# 九十一、网络/AI延迟提示

如果系统处理出现短暂延迟：

不要马上报错。

例如：

```text
正在识别当前操作……
```

如果持续超时：

```text
AI识别暂时不可用，已通知教师。
```

学生不需要理解具体服务错误。

---

# 九十二、训练过程中页面刷新怎么办

Runtime Session 存在服务端。

页面重新打开后：

```text
恢复当前 Session
```

而不是重新开始。

至少恢复：

```text
当前步骤
已完成步骤
当前用时
异常状态
```

否则真实课堂非常容易因为浏览器刷新造成训练丢失。

---

# 九十三、意外关闭浏览器

如果学生关闭页面，但摄像头/边缘推理还在运行：

需要根据部署模式决定。

一期产品规则建议：

> Session 保持运行一段时间，学生重新打开后恢复。

不要直接判训练结束。

---

# 九十四、教师端断线不影响学生训练

教师监控页面只是观察端。

教师电脑掉线：

> 学生 Runtime Session 继续运行。

这是架构上必须保证的。

---

# 九十五、学生端不能依赖教师页面持续在线

整个判定应该发生在：

```text
边缘节点 / 后端 Runtime
```

而不是：

> 教师页面打开才工作。

---

# 九十六、实时消息机制

从技术上学生端和教师端需要接收：

```text
Step State Change
Exception
Feedback
Teacher Action
System Status
```

可以采用：

```text
WebSocket
```

或者类似实时通道。

具体技术可以由研发选择。

产品只需要定义事件语义。

---

# 九十七、学生端 UI 不应直接消费原始 Event

前端不应该收到：

```text
pickup_torque_wrench
```

然后自己判断显示什么。

应该由后端输出：

```text
Runtime Feedback
```

例如：

```json
{
  "type": "STEP_COMPLETED",
  "stepId": "S07",
  "message": "本步骤已完成"
}
```

这样判定逻辑集中在服务端。

---

# 九十八、教师端同样消费业务状态

教师端获取：

```text
Station Status
Session Status
Attention Event
```

而不是直接解析视觉模型输出。

这样前端不会和 AI 模型高度耦合。

---

# 九十九、Attention Event

建议教师端增加一个专门对象：

```text
AttentionEvent
```

它不一定是正式 Exception。

例如：

```text
学生请求帮助
长时间停滞
AI连续无法判断
设备状态异常
```

都可以产生 Attention Event。

---

# 一百、Attention Event 分类

建议：

```text
STUDENT_HELP
AI_UNCERTAIN
LONG_STALL
SYSTEM_ERROR
HIGH_EXCEPTION
CRITICAL_SAFETY
```

教师驾驶舱只需要根据这些事件排序。

---

# 一百零一、Attention Event 生命周期

状态：

```text
OPEN
ACKNOWLEDGED
RESOLVED
```

例如：

```text
学生请求帮助
↓
OPEN
↓
教师点击查看
↓
ACKNOWLEDGED
↓
教师处理完成
↓
RESOLVED
```

避免老师和多个教师重复处理同一工位。

---

# 一百零二、教师“已关注”

点击异常工位后，可以自动：

```text
ACKNOWLEDGED
```

页面显示：

> 张老师正在处理。

如果多个教师同时带课，可以避免重复介入。

一期单教师场景可以先简化，但数据结构可以保留。

---

# 一百零三、教师离开详情后异常是否消失

不能。

只有异常真正：

```text
RESOLVED
```

才从“需要关注”中退出。

仅查看不代表解决。

---

# 一百零四、自动解决的 Attention Event

例如：

```text
AI_UNCERTAIN
```

学生重新执行后成功识别。

系统可以自动：

```text
RESOLVED
```

无需教师处理。

但历史仍保留。

---

# 一百零五、长时间停滞自动解除

学生继续操作后：

```text
LONG_STALL
→ RESOLVED
```

这样驾驶舱只展示当前真正需要注意的问题。

---

# 一百零六、教师监控详情中的时间轴

建议底部展示最近事件：

```text
10:22:01 S07开始
10:22:12 工具错误
10:22:16 系统提示
10:22:22 学生重新选择工具
10:22:27 操作恢复正常
```

教师不用翻所有 Event。

只看教学业务事件。

---

# 一百零七、教师查看 AI 原始详情

提供：

> 查看 AI 详情

进入高级面板。

例如：

```text
Event:
pickup_open_end_wrench

Confidence:
0.94

Source:
camera_03

Model:
tool_detector_v4.2
```

默认收起。

仅供排查误判。

---

# 一百零八、教师纠正 AI

训练过程中老师发现：

> 系统把扭矩扳手识别成开口扳手。

点击：

> AI判断错误。

这条反馈应该同时：

```text
解决当前异常
+
形成AI Feedback
```

一举两用。

---

# 一百零九、教师不应该能随意修改底层 AI 能力

例如：

> 以后把置信度从 0.8 调到 0.4。

这种操作不能放教师端。

教师只能：

> 对当前个案进行人工修正。

模型参数属于 AI Studio。

---

# 一百一十、训练报告与实时训练的连接

训练结束后的报告里点击：

> S07 工具选择错误。

进入视频：

```text
02:18
```

同时最好展示：

```text
当时系统给出的实时提示
```

例如：

> 当前工具选择错误，请重新选择。

这样学生能完整回忆训练过程。

---

# 一百一十一、结构化视频时间轴

训练视频不只是播放器。

时间轴上标注：

```text
S01
S02
⚠ S03
S04
⚠ S05
```

并支持筛选：

```text
全部
错误
教师介入
提示
```

这会比传统录像更有教学价值。

---

# 一百一十二、学生查看标准视频与自己的视频对照

一期可以采用简单方式：

```text
我的操作视频

标准操作视频
```

上下或左右播放。

不需要一开始做：

> AI动作骨架对比。

# 一百二十一、第一轮可用性测试

找真实老师和学生测试时，不先问：

> 你觉得页面好不好看。

重点观察：

### 学生

```text
是否知道下一步做什么
错误后是否知道怎么改
提示是否打断操作
标准视频是否方便查看
是否理解“已完成”
```

### 教师

```text
能否在10秒内发现最需要处理的学生
能否判断问题是什么
是否知道该点击什么进行人工确认
是否觉得系统减少了巡视压力
```

---

# 一百二十二、教师监控端最重要的可用性指标

假设：

```text
24个工位
其中3个出问题
```

教师打开系统后：

> 能不能在数秒内找到这3个人。

如果仍然需要：

> 一个视频一个视频看，

那么整个监控端设计就是失败的。

---

# 一百二十三、学生端最重要的可用性指标

学生发生错误以后：

> 能不能在不依赖教师解释的情况下理解错误并完成第一次纠正。

如果 AI 识别准确，但提示学生看不懂，也不能算真正成功。

---

# 一百二十四、课堂价值指标

```text

学生求助率
AI自动处理异常比例
学生平均重试次数
完成率
```

真正证明的是：

> AI有没有降低教师重复性巡查成本。

# 一百二十五、学生价值指标


# 一百二十六、完整课堂运行示例

以 30 人机械装配训练为例。

14:00：

教师发布任务。

学生到对应工位。

系统准备检查。

14:05：

30 个 Session 启动。

教师驾驶舱：

```text
正常：28
设备异常：2
```

教师先处理设备。

14:12：

系统出现：

```text
工位08 WRONG_TOOL
工位13 STUDENT_HELP
工位21 LONG_STALL
```

教师驾驶舱优先展示三人。

与此同时其他 27 人继续训练。

14:20：

系统发现：

```text
S07工具选择错误
已经有9人发生
```

教师暂停全班：

> 统一讲解工具使用。

然后恢复训练。

14:40：

大部分学生完成。

系统自动生成：

```text
个人训练报告
班级错误统计
步骤耗时
教师介入记录
```

教师课后不需要再人工整理 30 份观察表。

这才是这套产品完整的课堂价值。

# 一百二十七、产品不是用 AI 取代老师

这一层的合理角色分工应该是：

```text
AI：
持续观察
重复判断
实时记录
常规纠错
异常筛选

教师：
复杂判断
教学解释
个别指导
AI复核
最终评价
```

因此产品设计目标不是：

> 让教师离开实训室。

而是：

> 让一个教师能更有效地管理更多真实实训过程，并把注意力集中到真正需要人的地方。

# 一百二十八、与核心引擎的最终连接

学生实时训练端消费：

```text
Step State
Feedback
Attention Status
Standard Content
```

教师实时监控端消费：

```text

Exception
Manual Action
```

底层链路：

```text
Camera / Sensor
↓
AI Event Engine
↓
SOP Runtime Engine
↓
Exception / Step State
↓
Feedback Policy
↓
学生端

同时
↓

↓
教师监控端
```

训练结束：

```text
Session Finalization
↓
Assessment Engine
↓
学生报告
教师复核
班级分析
```

# 一百二十九、新增一个重要中间能力：Attention Engine

通过这一轮设计，我建议在整体架构中明确增加：

> **Attention Engine（教师关注引擎）**

它不是 AI 模型。

它负责从：

```text
异常
AI不确定
系统异常
学生求助
长时间停滞
安全事件
```

中判断：

> 哪些工位现在值得教师关注。

最终输出：

```text
AttentionEvent
```

这样教师驾驶舱和正式评分系统解耦。

---

# 一百三十、为什么需要 Attention Engine

因为：

```text
需要老师关注
```

和：

```text
学生应该扣分
```

不是一回事。

例如：

```text
AI连续识别失败
```

需要老师关注，但不能扣学生分。

```text
学生长时间停滞
```

值得老师帮助，也不一定扣分。

```text
摄像头离线
```

更应该老师处理，但完全不是学生错误。

因此 Attention Engine 很有必要。

# 一百三十一、最终前台运行架构

整体可补充为：

```text
                AI Event Engine
                       ↓
                 SOP Runtime
                       ↓
           ┌───────────┴───────────┐
           │                       │
       Exception              Step State
           │                       │
           ├─────────┐             │
           ↓         ↓             ↓
    Assessment   Attention     Feedback Policy
     Engine       Engine            │
       │            │               ↓
       ↓            ↓             学生端
   教师复核      教师监控端
```

这一架构会比简单的：

> AI识别 → 学生页面 → 教师页面

清晰很多。

# 一百三十二、一句话定义学生端

> **学生实时训练端的核心不是展示 AI，而是让学生在真实操作过程中获得恰到好处的步骤指导和即时纠错，并在不打断实操节奏的前提下逐步减少对教师的重复性依赖。**

---

# 一百三十三、一句话定义教师监控端

> **教师实训监控端的核心不是把几十路摄像头搬到屏幕上，而是利用 AI 持续观察全班，将真正值得教师关注的异常、求助、不确定和安全问题自动筛选出来，让教师从“逐个巡视”转变为“按需介入”。**

如果这两个前台做好，前面设计的 Event Engine、State Machine 和 Assessment Engine 才真正能够转化成课堂中的实际产品价值。
