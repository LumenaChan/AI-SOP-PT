# SOP Editor 功能详细设计

**版本：V1.0**  
**所属产品：AI 实训智能指导与考评平台**  
**模块定位：平台核心配置中心**

---

# 一、模块定位

SOP Editor 不是普通的“流程维护页面”，而是整套 AI-SOP 平台的核心生产工具。

它承担的核心任务是：

> 将教师或行业专家掌握的人工 SOP，转化为系统可以执行、AI 可以识别、评分引擎可以判断的“数字 SOP”。

因此，一个 SOP 在系统中不能只是：

```text
第一步：检查工具
第二步：安装零件
第三步：拧紧螺栓
```

而必须进一步结构化成：

```text
步骤
+
前后关系
+
机器识别条件
+
异常判断规则
+
评分规则
+
教学指导内容
+
能力评价映射
```

SOP Editor 最终需要解决两个完全不同的问题：

**对教师而言：**

> “我要怎么定义一个学生应该如何操作的标准流程？”

**对系统而言：**

> “我要依据哪些可观测事件，判断学生已经正确完成了这个步骤？”

所以产品设计必须保证：

> 教师看到的是教学语言，系统保存的是机器规则。

---

# 二、使用角色

一期建议 SOP Editor 主要存在三个角色。

### 1. 教师 / 专业负责人

负责：

创建 SOP、配置步骤、上传标准视频、配置步骤顺序、设置教学提示、设置分值和扣分规则、绑定已经存在的 AI 识别能力。

教师原则上不直接接触模型名称、训练参数和算法配置。

---

### 2. 实施人员 / AI 产品管理员

负责：

协助教师把实际 SOP 转成可识别规则，配置 ROI 区域、绑定 AI Event、调整识别阈值、确认哪些步骤 AI 当前能够识别。

这是一期非常重要的中间角色。

产品初期不应该假设：

> “老师自己就能完整配置 AI SOP。”

现实中很可能仍需要实施人员参与。

---

### 3. AI 工程人员

主要进入 AI Studio。

只在 SOP Editor 中查看：

> 当前 SOP 引用了哪些 AI Event、对应模型是否可用、当前能力是否已经发布。

原则上不负责修改教学规则。

---

# 三、核心对象层级

建议整个数据层级为：

```text
专业
└── 课程
    └── 实训项目
        └── SOP
            └── SOP版本
                └── Step
                    ├── 教学内容
                    ├── Recognition Rule
                    ├── Exception Rule
                    ├── Score Rule
                    └── Ability Mapping
```

例如：

```text
机械制造及自动化
└── 机械装配技术
    └── 减速器拆装实训
        └── 减速器标准拆装SOP
            └── V1.2
                ├── S01 穿戴防护用品
                ├── S02 检查工具
                ├── S03 固定减速器
                └── ...
```

这里必须将：

> **实训项目**

和：

> **SOP**

分开。

因为同一个实训项目以后可能存在：

```text
基础训练版 SOP
标准考试版 SOP
技能大赛版 SOP
企业标准版 SOP
```

不能把项目和流程强绑定成一对一。

---

# 四、SOP 生命周期

一个 SOP 建议包含以下状态：

```text
草稿
↓
配置中
↓
待验证
↓
验证通过
↓
已发布
↓
已停用
```

其中：

### 草稿

刚刚创建，仅存在基础信息。

### 配置中

已经开始编辑步骤和规则。

### 待验证

步骤配置基本完成，进入真实测试。

### 验证通过

通过规定测试用例，但尚未正式提供给学生使用。

### 已发布

可以用于训练任务或考试任务。

### 已停用

历史训练记录仍然保留，但不能再创建新任务。

一期不允许直接编辑“已发布版本”。

已发布之后如果需要修改：

```text
V1.0 已发布
↓
创建新版本
↓
V1.1 草稿
```

这样必须保留历史训练时实际使用的规则。

# 五、SOP Editor 总体页面布局

建议采用典型的“三栏式编辑器”。

```text
┌─────────────────────────────────────────────────────────────┐
│ ← 减速器标准拆装SOP   V1.2 草稿       [预览] [验证] [发布] │
├──────────────┬──────────────────────────┬───────────────────┤
│              │                          │                   │
│  步骤导航     │      当前步骤编辑区       │    规则配置区      │
│              │                          │                   │
│  S01 ✓       │   步骤名称               │   AI识别条件       │
│  S02 ✓       │   教学说明               │   判定逻辑         │
│  S03 ⚠       │   标准图片/视频           │   异常规则         │
│  S04         │                          │   评分规则         │
│  S05         │                          │   能力映射         │
│              │                          │                   │
│ +新增步骤     │                          │                   │
│              │                          │                   │
├──────────────┴──────────────────────────┴───────────────────┤
│ 当前版本存在 2 个配置问题                        [查看问题] │
└─────────────────────────────────────────────────────────────┘
```

三个区域职责必须明确：

**左侧：流程。**

解决：

> 有哪些步骤、顺序是什么。

**中间：教学。**

解决：

> 这一步学生到底应该怎么做。

**右侧：机器规则。**

解决：

> 系统到底凭什么认为学生完成了这一步。

---

# 六、顶部区域

顶部展示：

```text
SOP名称
所属实训项目
当前版本
当前状态
最后保存时间
负责人
```

主要操作：

```text
保存
预览
验证
发布
更多
```

“更多”中包括：

```text
复制SOP
创建新版本
导出配置
停用
删除草稿
```

一期不建议设计复杂的多人实时协同。

只需要基本的：

> 最后修改人 + 最后修改时间。

---

# 七、左侧步骤导航

左侧是整个 SOP 的结构树。

例如：

```text
01 穿戴防护用品               ✓
02 检查工具                   ✓
03 固定减速器                 ⚠
04 拆除端盖螺栓              ✓
05 取下端盖                   ✓
06 取出轴承                   ○
07 检查轴承                   ○
```

状态图标建议：

```text
✓ 配置完整
⚠ 存在问题
○ 尚未完成配置
```

点击步骤切换中间和右侧内容。

---

# 八、步骤新增方式

点击：

> - 新增步骤

弹出简单表单：

```text
步骤名称 *
步骤说明
插入位置
```

插入位置支持：

```text
添加到末尾
插入当前步骤之前
插入当前步骤之后
```

新增完成后自动进入步骤编辑。

---

# 九、步骤排序

一期建议支持拖拽。

例如：

```text
S04
拖到
S02后面
```

但这里有一个非常关键的问题：

不能简单调整 UI 顺序。

因为重新排序可能影响：

```text
前置步骤
评分逻辑
步骤依赖
异常判断
```

因此拖拽以后系统必须执行依赖检查。

比如原来：

```text
S03 前置步骤 = S02
```

如果将 S03 移到了 S01 前面，应提示：

> 当前调整可能导致步骤依赖关系异常，请检查 S03 的前置步骤。

一期不需要自动重写复杂规则。

---

# 十、步骤基本信息

每个步骤首先包含：

```text
步骤编号
步骤名称
步骤说明
是否必做
预计操作时长
```

步骤编号建议自动生成，不允许教师直接输入。

例如：

```text
S01
S02
S03
```

即使步骤重新排序，内部唯一 ID 不改变。

展示序号可以变化。

这样避免历史规则引用失效。

---

# 十一、教学内容配置

中间区域主要解决：

> 学生怎么学。

建议包括：

### 标准说明

支持富文本，但一期只需要：

```text
文字
重点提示
安全提示
```

例如：

> 使用指定扭矩扳手按照对角顺序完成端盖螺栓紧固。

---

### 标准图片

每个步骤支持上传若干张。

例如：

```text
正确工具
正确安装位置
正确完成状态
```

---

### 标准视频

建议一期就支持步骤级标准视频。

可以：

```text
上传单独步骤视频
```

或者：

```text
从整段标准SOP视频中截取 01:22–01:36
```

后者未来更重要。

---

### 注意事项

例如：

```text
禁止使用普通开口扳手代替
紧固前确认螺栓已经正确定位
```

这些内容用于训练模式提示。

考试模式默认不展示。

---

# 十二、流程规则

每个步骤需要配置：

```text
是否必做
前置步骤
是否允许跳过
是否允许重复执行
是否允许提前执行
```

一期暂不做复杂 BPMN。

例如：

```text
步骤：
S05 取下端盖

必做：
是

前置步骤：
S04 拆除端盖螺栓

允许提前：
否

允许重复：
否
```

这里已经足够覆盖绝大多数线性机械实训。

---

# 十三、步骤关系不要只依赖展示顺序

这一点必须在底层明确。

比如：

```text
S01
S02
S03
S04
```

UI 看起来是线性。

但真正逻辑必须保存为：

```text
S02 depends_on S01
S03 depends_on S02
S04 depends_on S03
```

否则后期加入：

```text
分支
并行
条件节点
```

架构会推翻。

一期 UI 可以简单，但底层模型不要只存：

```text
order = 1
order = 2
```

---

# 十四、AI 识别条件

右侧最核心区域为：

> **完成条件**

教师不需要写代码。

界面表现为：

```text
本步骤完成，需要满足：

[ + 添加识别条件 ]
```

添加以后：

```text
✓ 使用工具 = 扭矩扳手
✓ 操作动作 = 紧固
✓ 操作目标 = 端盖螺栓
```

默认关系：

> 同时满足全部条件。

即：

```text
AND
```

一期 UI 只提供：

```text
满足全部条件
满足任一条件
```

不开放任意嵌套表达式。

---

# 十五、识别条件类型

一期至少需要支持以下几类。

| 类型   | 示例          |
| ---- | ----------- |
| 对象存在 | 扭矩扳手出现在指定区域 |
| 动作事件 | 学生执行紧固动作    |
| 人物关系 | 学生拿取扳手      |
| 区域事件 | 手进入工具区      |
| 状态事件 | 螺栓处于已安装状态   |
| 人工确认 | 教师确认完成      |

虽然一期主技术是视觉，但 UI 层建议同时预留：

```text
设备事件
传感器事件
语音事件
```

暂时显示“暂未开放”即可。

---

# 十六、AI 能力选择器

点击：

> 添加识别条件

弹出能力选择器。

建议不是让教师看到：

```text
YOLOv11-tool-v3
pose-v2
```

而是看到：

```text
动作
  ├─ 拿取
  ├─ 放置
  ├─ 紧固
  ├─ 插入
  └─ 按压

工具
  ├─ 扭矩扳手
  ├─ 开口扳手
  ├─ 螺丝刀
  └─ 游标卡尺
```

每个能力展示：

```text
名称
类别
可用状态
适用场景
```

例如：

> 扭矩扳手识别  
> 状态：可用

或者：

> 游标卡尺读数识别  
> 状态：能力建设中

---

# 十七、当系统缺少某个 AI 能力时怎么办

这是非常关键的产品交互。

比如老师想配置：

> 检测学生使用塞尺。

但当前能力库没有“塞尺”。

不能直接让配置失败。

建议提供：

```text
未找到“塞尺”识别能力。

[申请新增AI能力]
```

点击以后形成：

```text
AI能力需求单
```

包含：

```text
来源SOP
来源步骤
能力名称
老师描述
参考图片/视频
需求人
```

交给技术团队。

未来 AI 能力建设完成以后，再回来绑定。

这能把：

> 产品配置

和：

> AI研发需求

真正串起来。

---

# 十八、ROI 区域配置

某些事件不能全画面判断。

例如：

> 学生必须从工具区取工具。

建议支持：

```text
工具区
装配区
危险区
检测区
```

ROI 配置由实施人员操作。

界面：

```text
选择摄像头
↓
截取当前画面
↓
鼠标框选区域
↓
命名区域
```

例如：

```text
Region ID:
tool_zone_01

名称：
工具放置区
```

步骤识别条件即可写：

```text
扭矩扳手
出现在
工具放置区
```

---

# 十九、识别置信度

一期不要让教师配置。

默认由 AI 能力管理后台提供推荐阈值。

例如：

```text
扭矩扳手识别
推荐阈值 0.85
```

实施人员可以在高级设置调整。

教师端只看到：

> 识别能力：正常。

否则很容易出现老师为了“识别更灵敏”随便调阈值，导致系统失控。

---

# 二十、持续时间规则

很多动作不能通过单帧判断。

例如：

> 手经过危险区域

和：

> 手真正伸入危险区域操作

含义不同。

因此识别条件可以增加：

```text
持续至少 X 秒
```

例如：

```text
紧固动作
持续至少：
2 秒
```

底层就是：

```text
action == tightening
duration >= 2s
```

但教师看到的还是自然语言。

---

# 二十一、步骤完成条件

完成条件建议支持：

```text
自动完成
人工确认
AI判断 + 人工确认
```

第一种：

> AI 条件满足后立即完成。

第二种：

> 学生操作以后，由教师点击确认。

第三种：

> AI先判断，但老师确认后才算完成。

这对一期非常有用。

因为不是所有步骤都能马上 AI 化。

这样即使一个 SOP 有 12 步：

```text
8步 AI自动识别
4步 教师确认
```

整个系统仍然可以先跑起来。

这个设计非常重要。

它能避免：

> 为了实现 100% AI 自动识别，把项目无限拖延。

---

# 二十二、异常规则

每个步骤右侧提供：

> 异常规则

默认根据识别条件自动提供常见异常：

```text
未执行
提前执行
顺序错误
错误工具
超时
```

教师可以：

```text
启用 / 禁用
```

并定义处理方式。

例如：

```text
错误工具

训练模式：
立即提示

考试模式：
记录异常

评分：
-2分
```

---

# 二十三、异常类型建议系统统一管理

一期建议平台内置统一异常码：

```text
STEP_MISSING
步骤遗漏

STEP_OUT_OF_ORDER
顺序错误

WRONG_TOOL
工具错误

WRONG_OBJECT
对象错误

WRONG_REGION
区域错误

TIMEOUT
步骤超时

SAFETY_VIOLATION
安全违规

AI_UNCERTAIN
AI无法确定
```

SOP只选择使用哪些异常。

不要每个 SOP 自己创建完全不同的异常名称。

这样以后才能做跨 SOP 统计。

---

# 二十四、安全规则

安全规则建议单独视觉强化。

例如：

> 未佩戴护目镜。

可以设置：

```text
异常等级：
严重

训练模式：
立即红色警告

考试模式：
记录

评分规则：
扣10分

是否终止：
否
```

再比如：

> 设备运行状态进入危险区域。

可以配置：

```text
异常等级：
红线

训练模式：
立即警告

考试模式：
立即终止

评分：
本项0分
```

一期虽然不一定接设备控制，但产品模型必须支持：

```text
一般异常
严重异常
红线异常
```

---

# 二十五、评分配置

评分规则必须属于 SOP，而不是写在 AI 算法里。

每个步骤：

```text
步骤标准分
```

例如：

```text
S07 紧固端盖螺栓
标准分：8
```

下面配置：

```text
未完成       -8
错误工具     -2
顺序错误     -2
超时         -1
```

产品必须处理一个问题：

> 一个步骤出现多个错误是否重复扣分。

因此一期建议提供：

```text
扣分方式：

○ 异常累计扣分，最低扣至0分
○ 只取最严重异常
```

默认：

> 累计扣分，最低为 0。

---

# 二十六、步骤评分和整场评分

SOP 顶部还要有：

> 考评设置

例如：

```text
总分：
100

合格分：
60

安全红线：
出现指定红线异常时考试不合格
```

系统应自动检查：

```text
所有步骤标准分合计
=
SOP总分
```

如果不一致：

> 当前步骤总分为 95 分，与 SOP 总分 100 分不一致。

禁止发布。

---

# 二十七、能力映射

步骤右侧最后一个区域：

> 能力评价

例如 S07：

```text
紧固端盖螺栓
```

关联：

```text
工具使用能力
装配规范能力
操作熟练度
```

每项可以分配权重：

```text
工具使用       40%
操作规范       40%
熟练程度       20%
```

一期不需要复杂算法。

主要目的就是：

> 为未来能力画像留下结构化数据。

---

# 二十八、能力指标库

能力不要每个 SOP 自由输入。

建议由平台统一维护一级能力。

例如机械类一期先配置：

```text
安全规范
流程规范
工具使用
操作熟练
完成质量
```

SOP步骤从能力库选择。

后续专业不同可以扩展。

---

# 二十九、整段标准视频

除了步骤视频，SOP 层面建议支持：

> 标准完整视频。

用户上传一段完整标准操作视频。

页面显示时间轴：

```text
00:00 ───────────────────── 12:34
```

教师或实施人员可以给步骤绑定：

```text
S01 00:12–00:36
S02 00:37–01:05
S03 01:06–01:44
```

最终得到：

> 一份视频，对应完整数字 SOP。

未来甚至可以做 AI 自动切步骤。

但一期人工标记即可。

---

# 三十、SOP 预览

点击：

> 预览

进入“学生视角预览”。

教师可以看到训练模式下学生最终看到什么。

例如：

```text
第 4 / 11 步

拆除端盖螺栓

操作要求：
使用指定工具依次拆除四颗螺栓。

[播放标准视频]

注意：
请按照对角顺序拆除。
```

这样教师不需要真正发布后再检查教学内容。

---

# 三十一、验证功能

这是 SOP Editor 里非常重要但容易遗漏的一块。

完成配置后不能直接发布。

点击：

> 验证 SOP

进入验证模式。

实施人员按照标准 SOP 实际操作一遍。

系统记录：

```text
S01 自动识别成功
S02 自动识别成功
S03 识别置信度不足
S04 自动识别成功
S05 未识别
```

验证结束生成：

```text
步骤总数：12
自动识别成功：10
人工确认：1
异常：1
```

未通过步骤可以直接进入配置调整。

---

# 三十二、验证不应该只是“正常操作”

正式发布前至少需要三类测试。

```text
标准操作测试
异常操作测试
边界测试
```

标准操作：

> 全部按照 SOP 完成。

异常操作：

> 故意漏步、错序、拿错工具。

边界测试：

> 动作做到一半取消、重复动作、快速操作。

一期不需要自动化测试框架。

但至少记录测试结果。

---

# 三十三、发布前自动校验

点击“发布”时必须执行完整校验。

例如：

```text
✓ SOP名称完整
✓ 至少1个步骤
✓ 每个必做步骤都有完成条件
✓ 所有依赖步骤存在
✓ 不存在循环依赖
✓ 步骤分值合计正确
✓ 所有AI能力均处于可用状态
⚠ S08没有标准视频
✓ 验证已通过
```

这里建议区分：

```text
错误
警告
```

错误必须修复。

警告允许发布。

例如：

**错误：**

> S05 引用了已经下线的 AI 能力。

**警告：**

> S08 未上传标准视频。

---

# 三十四、循环依赖必须阻止

例如教师不小心配置：

```text
S03 前置 S04
S04 前置 S03
```

这会产生死锁。

发布校验必须识别：

> 存在循环依赖：S03 → S04 → S03。

不能发布。

---

# 三十五、版本管理

正式发布后必须冻结。

例如：

```text
V1.0
2026-10-12发布
当前已有：
238条训练记录
42条考试记录
```

教师要修改：

> 第7步扣分从 -2 改成 -3。

不能直接改 V1.0。

点击：

> 创建新版本

生成：

```text
V1.1
```

继承 V1.0。

修改后重新验证、发布。

后续新任务默认使用 V1.1。

历史成绩继续关联 V1.0。

---

# 三十六、版本对比

一期建议做基础 Diff。

例如：

```text
V1.0 → V1.1

修改：
S07 错误工具扣分
-2 → -3

新增：
S09 标准操作视频

删除：
无
```

不需要做像 Git 那么复杂。

但教师必须知道：

> 新版本改了什么。

---

# 三十七、发布后的任务引用

训练任务创建时绑定：

```text
SOP_ID
+
SOP_VERSION
```

而不是只绑定 SOP。

例如：

```text
2026级机械1班
减速器拆装训练

SOP：
减速器标准拆装

版本：
V1.1
```

任务发布以后也不能自动升级到 V1.2。

否则学生前后训练标准会变化。

---

# 三十八、步骤复制

这是非常高频的操作。

例如：

```text
S07 安装第1颗螺栓
S08 安装第2颗螺栓
S09 安装第3颗螺栓
```

用户可以：

> 复制步骤

系统复制：

```text
教学内容
AI条件
异常规则
评分规则
能力映射
```

但自动生成新的 Step ID。

---

# 三十九、SOP 复制

后期不同机型可能非常类似。

例如：

```text
减速器A型拆装
减速器B型拆装
```

可以：

> 复制 SOP

然后修改：

```text
工具
工件
步骤
```

这会成为未来降低配置成本的重要能力。

---

# 四十、SOP Editor 中必须体现 AI 是否真的可用

不要出现一种假象：

> 教师把规则配好了，所以系统就能识别。

每个 AI 条件旁边建议显示状态：

```text
● 已发布
● 测试中
● 未配置
● 已停用
```

例如：

```text
紧固动作             ● 已发布
扭矩扳手             ● 已发布
端盖螺栓             ● 已发布
螺栓最终紧固状态      ● 测试中
```

如果必选能力不是“已发布”，SOP 不能正式发布。

---

# 四十一、AI能力引用关系

后台必须能反查：

```text
AI能力：
torque_wrench_detection
```

当前被哪些 SOP 使用：

```text
减速器拆装 V1.0
机械装配基础 V2.1
发动机拆装 V1.3
```

因为以后 AI 模型升级或者下线时，需要评估影响范围。

这实际上是平台化以后非常重要的依赖管理。

---

# 四十二、人工步骤是一期非常重要的降级机制

假设某个 SOP 有：

```text
12步
```

当前 AI 能稳定识别：

```text
9步
```

不要因为剩下三步 AI 做不到，就不让 SOP 上线。

剩余步骤可以设置：

```text
完成方式：
教师确认
```

或者：

```text
学生提交结果
+
教师确认
```

这样系统可以：

> AI 75% 自动化 + 人工 25%。

后续 AI 能力成熟以后再逐步替换。

这个策略对于一期落地非常关键。

---

# 四十三、AI无法确定时怎么办

AI Event Engine 必须允许：

```text
UNCERTAIN
```

而不是强制：

```text
正确 / 错误
```

例如置信度不足：

```text
0.62
```

进入：

```text
REVIEW_REQUIRED
```

考试结束交给教师复核。

这比系统胡乱给出一个确定答案可靠得多。

---

# 四十四、SOP Editor 和 AI Studio 的边界

最终一定要明确：

### SOP Editor 管：

```text
学生应该做什么
什么算完成
什么算错误
错误扣多少分
```

### AI Studio 管：

```text
机器怎么识别
使用哪个模型
训练数据是什么
指标是多少
模型部署在哪里
```

两个系统通过：

> **AI Event**

连接。

例如 SOP Editor 只引用：

```text
EVENT:
pickup_torque_wrench
```

至于这个 Event 底层用了：

```text
YOLO
+
Pose
+
Tracking
+
Rule
```

教师完全不用知道。

---

# 四十五、一期页面最核心的交互原则

整个 SOP Editor 建议遵循一个原则：

> **默认简单，高级能力逐步展开。**

教师第一次打开一个步骤，只应该看到：

```text
步骤名称
教学说明
标准视频
完成条件
异常规则
分值
```

而下面这些：

```text
ROI
置信度
持续时长
事件参数
高级逻辑
```

全部放在：

> 高级设置

否则整个系统会变成工程配置软件，教师根本无法使用。

---

# 四十六、页面默认状态建议

新建一个步骤后：

```text
步骤名称：
未命名步骤

是否必做：
是

完成方式：
AI自动判断

识别条件：
暂无

异常规则：
默认开启“未完成”

标准分：
0

能力映射：
暂无
```

页面顶部直接显示：

> 当前步骤尚未完成配置。

---

# 四十七、步骤完整性提示

每个步骤都可以计算配置状态。

例如：

```text
基础信息       ✓
教学内容       ✓
AI识别条件     ⚠
异常规则       ✓
评分规则       ✓
```

左侧就可以显示：

> S05 ⚠

点击以后直接告诉教师：

> 尚未配置“完成条件”。

这比等到发布时一次弹出几十个错误好很多。

---

# 四十八、未来二期能力预留

一期 UI 不需要实现，但数据模型最好提前考虑：

```text
条件分支
并行步骤
循环步骤
不同设备对应不同流程
步骤可选组
多个正确操作路径
动态评分规则
多人协同操作
```

例如未来可能存在：

```text
检查结果正常
→ S05

检查结果异常
→ S05A 故障处理
```

因此不要把 SOP 数据结构彻底锁死为纯数组。

---

# 四十九、最终核心数据对象

从系统实现角度，我建议至少拆为：

```text
SOP
SOPVersion
SOPStep
StepDependency
StepInstruction
StepRecognitionRule
RecognitionCondition
StepExceptionRule
StepScoreRule
StepAbilityMapping
SOPMedia
SOPValidation
AIEventReference
```

不要把一个步骤所有配置都塞进一个 JSON 大字段。

规则细节可以使用 JSON，但业务对象本身建议结构化。

# 五十、一期 SOP Editor 成功标准

这个模块是否成功，不应该只看页面是否能保存 SOP。

真正应该看：

> 一个非研发人员，在实施人员辅助下，是否能够把一个真实纸质 SOP 配成系统 SOP。

以及：

> 第二个 SOP 是否可以明显复用第一个 SOP 已有的 AI 能力。

建议一期做完以后实际找一名专业教师进行测试：

给他：

```text
纸质SOP
标准操作视频
评分表
```

让他完成一份 SOP 配置。

产品团队只观察：

```text
哪里不会用
哪里不知道如何配置
哪些教学术语和系统术语不一致
哪些步骤AI根本无法表达
```

这一轮测试的价值可能比继续加十个后台页面都大。

---

# 五十一、一期建议优先制作的原型页面

如果现在开始让 Codex 做产品原型，我建议不要一次制作整个 SOP Editor。

先完成以下核心链路：

```text
SOP列表
↓
新建SOP
↓
SOP Editor
↓
新增步骤
↓
绑定标准视频
↓
配置AI完成条件
↓
配置异常规则
↓
配置评分
↓
SOP预览
↓
发布校验
↓
发布版本
```

先把这条链路交互完整跑通。

然后再补：

```text
验证记录
版本对比
AI能力申请
ROI配置
```

# 五十二、SOP Editor 产品价值总结

SOP Editor 最终不是一个“流程编辑器”。

它真正承担的是三种语言之间的翻译：

```text
行业专家语言

“用扭矩扳手按照规定顺序紧固螺栓”

            ↓

机器语言

tool = torque_wrench
action = tightening
target = bolt
order = valid

            ↓

教学评价语言

工具使用正确
操作顺序正确
步骤完成
得5分
```

所以整个平台真正困难的，不只是 AI 模型。

而是建立一种：

> **把人类操作规范稳定转化为机器可观测规则的产品方法。**

如果 SOP Editor 能做到这一点，那么以后新增一个专业，并不是“重新开发一个系统”，而是在已有平台上：

> 增加新的 SOP + 增加少量新的 AI Event + 复用已有能力。

这就是这套产品最终从项目型系统走向平台型产品的核心。
