# 首个 PoC SOP 场景详细设计

**版本：V1.0**  
**所属产品：AI 实训智能指导与考评平台**  
**PoC 场景：机械零部件标准装配实训**  
**目标：验证 AI-SOP 从“标准流程配置—视觉识别—状态机判断—实时纠错—自动评分—教师复核—视频复盘”的完整技术与产品闭环**

---

# 一、PoC 为什么选择机械零部件标准装配

首个 PoC 不应该选择最复杂、最能体现“机械专业特色”的实训项目，而应该优先选择一个：

- 步骤清晰；

- 工位固定；

- 单人完成；

- 工具数量有限；

- 操作区域固定；

- 视觉可观察性强；

- 遮挡相对较少；

- 容易故意设计错误；

- 可以测试工具、动作、顺序、区域和状态；

- 第二套 SOP 可以复用大量已有能力。

因此首个 PoC 暂定：

> **机械零部件标准装配实训**

它不是某一所学校现有课程的最终版本，而是一个专门用于验证平台核心能力的标准 PoC。

后续正式进入学校时，应再根据真实实训指导书和教师评分表替换为实际项目。

---

# 二、PoC 核心目标

这个 PoC 不追求：

> “把机械装配所有复杂动作都识别出来。”

而是要证明五件事。

第一，视觉模型能够稳定识别一组有限工具、工件和操作区域。

第二，系统能够将连续视频转换成标准 AI Event。

第三，SOP Runtime 能够根据事件判断：

```text
当前步骤
步骤完成
漏步
错序
错工具
错误对象
重复操作
超时
```

第四，学生训练端能够实时纠错。

第五，同一套 Event 能力可以继续复用于第二套机械拆卸 SOP。

---

# 三、建议工位结构

PoC 采用：

> 单学生、单工位、固定桌面式装配。

工位建议包含：

```text
┌──────────────────────────────────┐
│                                  │
│          装配区域                 │
│                                  │
│       [底座] [零件A]             │
│                                  │
├───────────────┬──────────────────┤
│   工具区       │     零件区       │
│               │                  │
│ 扭矩扳手       │ 零件A            │
│ 开口扳手       │ 螺栓             │
│               │                  │
├───────────────┴──────────────────┤
│            成品区域               │
└──────────────────────────────────┘
```

重点是：

> 工具和工件位置尽量标准化。

PoC 阶段不要故意制造过于自由的工位布局。

---

# 四、摄像头建议

一期建议采用两个机位。

## 4.1 主摄像头

位置：

> 工位前上方斜俯视。

主要负责：

```text
人体
手部
工具
工件
拿取
放置
装配动作
```

---

## 4.2 顶视摄像头

位置：

> 工位正上方。

主要负责：

```text
工具区
零件区
装配区域
物体位置变化
进入/离开ROI
```

如果预算或开发时间有限，第一阶段可以先单机位。

但最终 PoC 建议至少测试一次双机位。

---

# 五、PoC 使用对象

建议准备：

```text
1个装配底座
1个零件A
2～4颗螺栓
1把扭矩扳手
1把开口扳手
1副防护眼镜
1副手套
```

其中：

> 扭矩扳手和开口扳手故意保留外观差异明显。

不要第一版就选择两种非常相似的工具。

PoC 首要任务是验证产品闭环，不是挑战视觉极限。

---

# 六、建议 SOP 总体步骤

首个 PoC 暂定 12 步。

```text
S01 穿戴规定防护用品
S02 检查装配工件
S03 取出零件A
S04 将零件A放置到装配位置
S05 取出螺栓
S06 将螺栓安装到指定位置
S07 取出扭矩扳手
S08 对螺栓执行第一次紧固
S09 对螺栓执行第二次紧固
S10 检查装配完成状态
S11 将工具归位
S12 将成品放入完成区域
```

这 12 步已经足够覆盖几乎所有核心系统能力。

---

# 七、S01 穿戴规定防护用品

## 标准要求

学生进入正式训练前应佩戴：

```text
防护眼镜
手套
```

## AI识别对象

```text
person
safety_glasses
gloves
```

## Event

```text
ppe_detected(
  type=safety_glasses
)

ppe_detected(
  type=gloves
)
```

## 完成条件

```text
safety_glasses == detected
AND
gloves == detected
```

持续：

> 例如连续确认 1 秒以上。

## 异常

```text
PPE_MISSING
```

## 教学处理

训练模式：

> 提示学生正确佩戴。

考试模式：

> 记录异常。

## PoC 价值

验证：

```text
人体识别
PPE识别
全局安全规则
训练前置条件
```

---

# 八、S02 检查装配工件

这一阶段不建议让 AI 判断“检查动作是否专业”。

先简化成：

> 学生需要将手依次进入零件区，对规定工件进行操作确认。

## AI对象

```text
part_A
bolt
```

## Event

```text
hand_enter_region(part_zone)
object_detected(part_A)
object_detected(bolt)
```

## 完成方式

一期建议：

> AI + 学生确认。

例如页面：

```text
请检查零件和螺栓是否齐全。

[确认检查完成]
```

系统同时确认：

> 当前画面中存在规定对象。

## PoC 价值

验证：

> 并非每个教学步骤都必须全自动 AI。

---

# 九、S03 取出零件A

## 标准行为

从零件区拿起：

> part_A。

## Event

```text
pickup_object(
  object=part_A,
  sourceRegion=part_zone
)
```

## 完成条件

```text
pickup(part_A)
```

## 异常

如果拿起错误对象：

```text
WRONG_OBJECT
```

## 故意错误

准备一个：

```text
part_B
```

作为干扰对象。

学生故意拿 part_B。

系统应提示：

> 当前零件选择错误。

## PoC 价值

验证：

```text
对象识别
拿取事件
错误对象
```

---

# 十、S04 将零件A放置到装配位置

## Event

```text
object_enter_region(
  object=part_A,
  region=assembly_zone
)
```

并结合：

```text
put_down_object(part_A)
```

## 完成条件

```text
part_A进入assembly_zone
AND
完成放置
```

## 异常

如果放到：

```text
finished_zone
```

产生：

```text
WRONG_REGION
```

## PoC 价值

这是非常适合一期的稳定事件。

主要测试：

```text
对象跟踪
ROI
区域关系
放置
```

---

# 十一、S05 取出螺栓

## Event

```text
pickup_object(
  object=bolt
)
```

如果存在多颗螺栓，不要求区分具体实例。

只需要：

```text
objectClass = bolt
```

## 完成条件

学生拿到螺栓。

## PoC 价值

验证：

> 小对象是否能稳定检测。

如果这一项视觉效果差，可以通过：

```text
固定螺栓托盘
更明显的背景对比
```

提高识别稳定性。

---

# 十二、S06 将螺栓安装到指定位置

这一动作比普通拿取复杂。

一期不建议直接训练：

> install_bolt_model。

建议采用组合事件。

```text
person_holding_object(bolt)
AND
bolt_enter_region(bolt_install_zone)
AND
bolt_present_after_operation
```

最终输出：

```text
bolt_installed
```

## 完成条件

```text
bolt_installed == true
```

## PoC 价值

验证：

> 动作过程 + 最终状态双重判断。

---

# 十三、为什么 S06 不能只看“手放过去了”

因为学生可能：

```text
做了安装动作
但螺栓没有真正放进去
```

所以建议最终状态：

```text
bolt_present
```

比纯动作更重要。

这是 PoC 中应该重点验证的一个设计原则：

> **有条件时，结果状态优先于单纯动作。**

---

# 十四、S07 取出扭矩扳手

这是整个 PoC 最关键的演示步骤之一。

## 正确 Event

```text
pickup_object(
  object=torque_wrench,
  sourceRegion=tool_zone
)
```

## 干扰工具

```text
open_end_wrench
```

## 故意错误

学生先拿：

> 开口扳手。

SOP 要求：

> 扭矩扳手。

产生：

```text
WRONG_TOOL
```

训练端显示：

> 当前工具选择错误，请使用规定工具。

学生放回错误工具后重新拿取扭矩扳手。

最终：

```text
S07 COMPLETED
```

但历史：

```text
WRONG_TOOL ×1
```

保留。

---

# 十五、S07 是整个产品价值演示的重点

因为它可以非常完整地展示：

```text
AI识别
↓
SOP规则
↓
异常
↓
学生实时提示
↓
学生纠错
↓
步骤继续
↓
异常仍计入报告
↓
评分扣分
↓
视频证据
```

这是建议演示时重点设计的一段。

---

# 十六、S08 第一次紧固

## 标准行为

学生持有：

```text
torque_wrench
```

对：

```text
bolt
```

执行：

```text
tightening
```

## Event 组合

```text
person_holding_tool(torque_wrench)
AND
tool_contact_target(bolt)
AND
rotation_action
AND
duration >= X
```

生成：

```text
tighten_bolt
```

---

# 十七、PoC 阶段不要识别真实扭矩数值

普通摄像头无法可靠判断：

> 是否真的达到 35Nm。

因此一期：

> 只判断“使用规定工具完成紧固动作”。

真实扭矩值未来通过：

```text
智能扭矩扳手
Sensor Event
```

接入。

这一点应该明确写进 PoC 边界。

---

# 十八、S09 第二次紧固

S09 与 S08 使用同一套 Event。

这一步非常重要。

因为它能够验证：

> 同一个 Event 能力可以在同一个 SOP 的多个步骤中复用。

例如：

```text
tighten_bolt
```

既用于：

```text
S08
```

又用于：

```text
S09
```

区别由：

```text
target region
step order
runtime context
```

决定。

---

# 十九、S08/S09 必须设计错序测试

标准：

```text
S08 → S09
```

测试人员故意：

> 跳过 S08，直接执行 S09 对应目标。

系统应产生：

```text
STEP_OUT_OF_ORDER
```

然后根据规则要求：

> 返回完成 S08。

---

# 二十、如果两个紧固点长得一样怎么办

这是真实 PoC 很容易遇到的问题。

如果：

```text
bolt_A
bolt_B
```

视觉外观完全相同，

不要强行训练：

> 这是 A 螺栓，这是 B 螺栓。

可以依赖：

```text
ROI
```

例如：

```text
bolt_zone_A
bolt_zone_B
```

判断操作目标。

这是非常典型的：

> 用产品和场景设计降低算法难度。

---

# 二十一、S10 检查装配完成状态

这个步骤可以有两种方案。

## 方案 A：AI状态检测

识别：

```text
part_A_installed
bolt_A_present
bolt_B_present
```

全部满足：

```text
assembly_complete
```

## 方案 B：AI + 人工确认

页面：

> 请检查零部件是否安装完整。

AI确认关键对象存在。

学生/教师：

> 点击确认。

一期建议优先采用：

> AI + 人工确认。

因为最终装配质量的细微判断通常更复杂。

---

# 二十二、S11 工具归位

要求：

```text
torque_wrench
```

重新进入：

```text
tool_zone
```

并停止移动。

Event：

```text
object_enter_region(
  object=torque_wrench,
  region=tool_zone
)
```

```text
put_down_object
```

最终：

```text
tool_returned
```

---

# 二十三、S11 可以故意测试漏步

测试人员完成装配后：

> 不归还工具。

直接进入 S12。

Runtime 应先产生：

```text
POTENTIAL_MISSING
```

考试结束时确认：

```text
STEP_MISSING
```

这可以很好地验证漏步逻辑。

---

# 二十四、S12 将成品放入完成区域

要求：

```text
assembled_part
```

进入：

```text
finished_zone
```

Event：

```text
object_enter_region(
  object=assembled_part,
  region=finished_zone
)
```

完成后：

```text
S12 COMPLETED
```

如果所有 required Step 完成：

```text
Session COMPLETED
```

# 二十六、PoC 必须预先设计测试用例

不能算法做好以后：

> 随便找几个人试试看。

应该提前定义标准 Case。

建议至少 15 个。

# 二十七、Case 01：完全正确

学生全程按照标准 SOP。

预期：

```text
12 / 12 COMPLETED
0 异常
```

如果评分总分 100：

```text
AI建议分：100
```

用途：

> 基础正常流程。

---

# 二十八、Case 02：错误对象

S03：

学生拿：

```text
part_B
```

预期：

```text
WRONG_OBJECT
```

训练模式提示后重新拿 A。

最终：

```text
S03 COMPLETED
```

异常保留。

---

# 二十九、Case 03：错误区域

S04：

学生将零件 A 放进：

```text
finished_zone
```

预期：

```text
WRONG_REGION
```

重新放到：

```text
assembly_zone
```

完成。

---

# 三十、Case 04：错误工具后纠正

S07：

先拿：

```text
open_end_wrench
```

预期：

```text
WRONG_TOOL
```

重新拿：

```text
torque_wrench
```

S07 完成。

重点验证：

> 错误不会让 Step 永久失败。

---

# 三十一、Case 05：错工具后不纠正

学生一直使用：

```text
open_end_wrench
```

尝试执行紧固。

预期：

```text
WRONG_TOOL
```

S07/S08 不应正常完成。

训练模式持续阻止流程自然推进。

---

# 三十二、Case 06：跳过 S07

学生没有正式拿扭矩扳手，直接尝试紧固。

根据 Event 能否观察到：

```text
tighten with torque_wrench
```

如果无法成立：

> S07保持未完成。

后续应产生：

```text
OUT_OF_ORDER / MISSING
```

---

# 三十三、Case 07：S08/S09 错序

学生直接操作：

```text
bolt_zone_B
```

而当前应：

```text
bolt_zone_A
```

预期：

```text
STEP_OUT_OF_ORDER
```

---

# 三十四、Case 08：漏掉工具归位

完成紧固后直接：

> 将成品放入 finished_zone。

预期：

```text
S11 potential missing
S12 out of order
```

Session 结束：

```text
S11 STEP_MISSING
```

---

# 三十五、Case 09：重复执行

S07 完成以后：

学生再次：

> 放回扳手又重新拿起。

如果步骤配置：

```text
allowRepeat = false
```

且形成完整重复操作，

产生：

```text
DUPLICATE_OPERATION
```

但不要因为基础 rotation 重复而误判。

---

# 三十六、Case 10：超时

S08：

学生拿着工具长时间不进行操作。

超过：

```text
maxOperationTime
```

产生：

```text
STEP_TIMEOUT
```

之后学生继续正确完成。

最终：

```text
S08 COMPLETED
+
TIMEOUT Exception
```

---

# 三十七、Case 11：AI不确定

人为制造：

```text
手部遮挡
工具部分遮挡
```

Event confidence 落入 Review 区间。

预期：

```text
AI_UNCERTAIN
```

训练模式：

> 要求重新操作。

连续失败：

> 请求教师确认。

---

# 三十八、Case 12：教师人工确认

S10 检查结果。

AI只能确认部分状态。

教师点击：

> 确认完成。

生成：

```text
MANUAL_EVENT
```

S10：

```text
COMPLETED
```

---

# 三十九、Case 13：系统摄像头掉线

训练过程中模拟：

```text
camera offline
```

预期：

```text
SYSTEM_EXCEPTION
```

而不是：

```text
STEP_MISSING
```

相关步骤进入：

> 待确认或暂停。

学生不扣分。

---

# 四十、Case 14：安全违规

例如 S01 未戴护目镜就开始操作。

预期：

```text
SAFETY_VIOLATION
```

训练模式：

> 阻止正式训练开始。

考试模式：

> 根据规则记录扣分或不合格。

---

# 四十一、Case 15：学生主动结束

在 S08 时点击：

> 结束训练。

最终：

```text
S09–S12
STEP_MISSING
```

训练报告显示：

> 未完成。

```text
STEP_TIMEOUT        -1
DUPLICATE_OPERATION -1
STEP_MISSING        当前步骤0分
```

安全异常：

```text
PPE_MISSING
-5
```

严重安全红线后期再根据真实课程规则调整。

# 四十八、数据采集设计

每个关键事件都需要：

```text
正样本
负样本
困难样本
```

不要只采标准操作。

例如拿扭矩扳手：

### 正样本

```text

快速拿起
慢速拿起
左手拿
右手拿
```

### 负样本

```text
手从上方经过
触碰但不拿
移动旁边工具
拿开口扳手
整理工具区
```

### 困难样本

```text
手遮挡工具
身体遮挡
工具部分露出
两把工具距离很近
```

# 六十二、Event 级建议验收口径

PoC 不建议一开始强行要求：

> 所有 Event ≥99%。

不同 Event 难度不同。

但建议建立：

```text
Precision
Recall
Latency
```

三个指标。

并根据业务严重程度设不同门槛。

例如：

### 工具选择

误判会导致错误提示。

因此：

> Precision 要高。

### 学生操作完成

漏检可能导致步骤卡住。

因此：

> Recall 同样重要。

---

# 六十三、安全事件必须更严格

安全 Event：

```text
PPE_MISSING
```

误判和漏判都很敏感。

不能与普通：

```text
tool_returned
```

采用同一个指标要求。

这也是为什么不要定义一个：

> 全平台 AI 准确率 ≥95%。

这种指标没有实际意义。

---

# 六十四、SOP Runtime 验收用例

建议每个 Case：

```text
重复执行20次以上
```

至少得到：

```text
预期结果
实际结果
是否一致
```

最终形成：

> Case Pass Rate。

例如：

```text
Case 04 错工具后纠正

20次
正确识别19次

Pass Rate：
95%
```

# 六十五、完整 Session 一致率

最值得关注：

> AI系统最终形成的完整操作记录与教师人工记录的一致程度。

让教师独立观察全过程，形成：

```text

```

再与系统比较：

```text
步骤
异常
顺序
时间
```

这比单模型 mAP 更接近最终产品质量。

# 七十六、第二套 PoC 才是真正的平台验收

记录：

```text

第二套所需Event总数
直接复用多少
```

```text
= 86.7%
```

这比：

> 第一套准确率 98%。

更能说明产品是否值得继续投资。

# 八十、SOP 机器可观测性分析表字段

例如：

| 步骤  | 教学标准    | AI可观测内容 | 感知方式   | 当前支持 | 风险    |
| --- | ------- | ------- | ------ | ---- | ----- |
| S07 | 取扭矩扳手   | 工具类别+拿取 | 视觉     | 是    | 遮挡    |
| S08 | 紧固至35Nm | 紧固动作    | 视觉     | 部分   | 无法测扭矩 |
| S08 | 达到35Nm  | 扭矩值     | Sensor | 否    | 需智能工具 |

这张表能提前暴露：

> 哪些教学要求根本不能靠普通摄像头实现。

---

# 八十一、每个步骤建议分成四种可实现程度

```text
A 完全AI自动识别
B AI识别 + 人工确认
C 设备/传感器实现
D 暂时纯人工
```

例如：

```text
S07 A
S08 B
真实扭矩 C
复杂质量 D
```

这样不会为了“AI自动化”把系统设计得不现实。

---

# 八十二、这张表也决定一期范围

如果某一个真实学校 SOP：

```text

```

分析后发现：

```text
A类 5
B类 3
C类 7
D类 5
```

而学校又没有任何设备接口。

那么它很可能不适合作为首个视觉 PoC。

```text
工位稳定性
操作顺序固定性
```

选择：

> 最适合平台验证的项目。

而不是单纯选择学校最想展示的项目。

# 八十五、真正决定是否进入下一阶段的 Gate

首个 PoC 完成后不要默认：

> 做完了就继续扩专业。

应该明确设置 Go / No-Go Gate。

至少问：

```text
AI事件能否稳定输出？
状态机是否能够解释真实过程？
教师是否愿意依赖系统？
学生提示是否真正可用？
视频证据是否能解释AI判定？
第二SOP接入是否明显更快？
```

如果最后一项没有改善：

> 重点应该回头优化平台抽象，

而不是立刻做第三个专业。

# 八十六、最危险的成功假象

第一套 SOP 演示效果很好。

老板觉得：

> 产品已经成功。

但实际上底层是：

```text
大量if else
大量针对这个工位的Hard Code
大量单独训练模型
```

第二个 SOP 重新开发。

这种情况应该被判定为：

> **PoC 技术演示成功，但平台产品验证失败。**

一定要区分。

# 八十七、首个 PoC 的最高验收原则

第一套 SOP 必须做到：

> 正确。

第二套 SOP 必须做到：

> 更快。

前者证明：

> 能做。

后者证明：

> 值得做成产品。

> 新建算法项目。

# 八十九、建议首个 PoC 的最终演示脚本

给学校或老板演示时，不要只是：

> 看，AI能识别扳手。

完整演示应该这样走。

学生进入：

```text
S01 PPE
```

系统自动识别。

正常完成 S02～S06。

到 S07：

> 学生故意拿错开口扳手。

学生端实时提示：

> 工具选择错误。

教师端同时看到：

> 工位03需要关注。

学生放回。

拿正确扭矩扳手。

继续操作。

S08/S09 故意错序一次。

系统再次记录。

S11 故意漏做。

训练结束。

系统生成：

```text
成绩
异常
步骤轨迹
视频时间轴
```

点击：

> 工具选择错误。

视频自动跳到对应片段。

教师复核：

> AI判断正确。

学生查看：

> 自己的错误视频 + 标准视频。

最后教师进入班级分析：

> 查看多个学生的共性错误。

这套演示才真正能体现：

> AI-SOP 是产品，而不是算法 Demo。

# 九十、一句话定义首个 PoC

> **首个 PoC 的任务，不是证明摄像头能够识别几个机械动作，而是用一个控制复杂度的真实机械装配流程，验证“机器感知—流程判断—教学纠错—自动评价—人工复核—视频证据—能力复用”的整个 AI-SOP 产品机制是否成立。**

首个 PoC 结束之后，必须立即用第二套 SOP 验证复用，否则第一套做得再漂亮，也只能说明“我们做出了一个项目”，还不能说明“我们做出了一个平台”。
