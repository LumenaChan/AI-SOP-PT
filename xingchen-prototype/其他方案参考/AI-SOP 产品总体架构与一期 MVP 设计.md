# AI-SOP 产品总体架构与一期 MVP 设计

**版本：V1.0**  
**适用场景：职业院校机械、机电、电气、汽修、轨交等真实工位实训**  
**一期目标：完成一个可真实运行、可复制第二个 SOP 的产品闭环，而非展示型 AI Demo**

---

# 一、产品定位

产品暂定定位为：

> **AI 实训智能指导与考评平台**

底层核心产品能力为：

> **AI-SOP Engine（智能实训 SOP 引擎）**

平台面向职业院校真实实训工位，通过摄像头、设备接口和传感器采集学生实操过程，将学生实际行为转化为标准化“操作事件”，与预先配置的标准 SOP 进行实时比对，从而完成训练指导、错误纠正、过程记录、自动考评、教师复核和学习分析。

产品需要解决的并不是简单的：

> “AI 看到了学生做了什么。”

而是进一步回答：

> “学生现在应该做什么、实际上做了什么、操作是否符合 SOP、哪里不符合、为什么扣分、老师如何复核、学生下一次应该改什么。”

2026 年《职业院校人工智能应用指引》已经明确提出，对于强调操作性的实训项目，可使用 AI 进行实训引导与实操动作纠偏；对于岗位任务链清晰、操作过程可分解的实训项目，可以利用 AI 对学生技能操作行为进行分析。这与本产品选择的“可分解 SOP + 动作事件 + 实时指导”方向高度一致。

---

# 二、一期首先明确：我们不做什么

一期最危险的问题不是功能少，而是目标太大。

因此一期暂不把产品定义成“能够识别所有机械实训动作的通用 AI”。

一期也不追求教师上传一段视频后，AI 自动理解整个 SOP，更不追求通用视觉大模型直接判断所有操作。

一期真正要验证的是：

> **我们能否把一个真实教学 SOP 转化成机器可理解的规则，并让系统稳定完成实时识别、步骤判断、错误发现、自动评分和视频复核。**

更重要的是验证第二个 SOP。

如果第一个 SOP 需要技术团队开发两个月，而第二个还是需要两个月，那么做出来的是：

> 项目。

如果第一个需要两个月，第二个只需要两周，第三个继续缩短，那么才开始具备：

> 平台能力。

所以一期产品的真正北极星指标不是某一个动作识别准确率，而是：

> **新 SOP 接入成本。**

# 四、系统最核心的数据模型：不要直接“识别步骤”

这是整个技术架构中最重要的一点。

不建议训练一个模型直接输出：

```text
当前正在执行：
第7步——紧固A点螺栓
```

而应该拆成：

```text
检测到：

person = student_01
tool = torque_wrench
action = tightening
target = bolt_A
region = assembly_zone_A
startTime = 10:32:15
duration = 4.3s
confidence = 0.94
```

形成标准化事件：

```json
{
  "eventType": "VISUAL_ACTION",
  "operator": "student_01",
  "action": "tightening",
  "object": "torque_wrench",
  "target": "bolt_A",
  "region": "assembly_zone_A",
  "timestamp": "2026-09-18T10:32:15.221",
  "duration": 4.3,
  "confidence": 0.94
}
```

SOP Engine 再根据当前执行状态判断：

```text
当前应该执行 S07

S07要求：
tool = torque_wrench
action = tightening
target = bolt_A
region = assembly_zone_A

事件满足要求

↓

S07视觉条件满足
```

如果同时要求扭矩 ≥ 30N·m，则继续等待：

```json
{
  "eventType": "SENSOR_VALUE",
  "sensor": "torque_wrench_01",
  "metric": "torque",
  "value": 33.4,
  "unit": "Nm"
}
```

两个条件全部成立之后：

```text
S07 = COMPLETED
```

这样系统以后才能自然扩展 PLC、语音、智能工具和传感器，而不是被视觉算法绑死。

# 五、统一事件模型

底层建议从一期开始统一定义五类事件。

| 事件类型         | 典型来源     | 示例              |
| ------------ | -------- | --------------- |
| Visual Event | 摄像头      | 拿取扳手、进入区域、拧紧    |
| Speech Event | ASR      | 学生完成规定口述        |
| Device Event | PLC/设备接口 | 设备启动、按钮触发、程序运行  |
| Sensor Event | 智能工具/传感器 | 扭矩 35N·m、电压 24V |
| Manual Event | 教师/学生    | 教师确认、人工复核       |

一期真正实现：

**Visual Event + Manual Event。**

但数据结构同时保留另外三种。

这样不会过度开发，也避免后期推翻系统。

# 六、AI Event Engine 怎么设计

AI Event Engine 不应该围绕某个专业建设，而应该逐步形成几个可复用的“能力库”。

| 能力库   | 示例                  |
| ----- | ------------------- |
| 人体能力库 | 人体检测、身份跟踪、姿态、关键点    |
| 动作能力库 | 拿、放、插、拔、拧、按、旋转、移动   |
| 工具库   | 扳手、螺丝刀、钳子、万用表、游标卡尺  |
| 工件库   | 螺栓、轴承、零件、电线、端子      |
| PPE库  | 手套、安全帽、防护镜          |
| 区域库   | 取料区、装配区、危险区、设备区     |
| 状态库   | 已安装、未安装、打开、关闭、连接、断开 |
| 关系库   | 人拿工具、工具接触工件、物体进入区域  |

一个 SOP 不应该拥有独立的全部 AI 能力。

而应该引用这些能力。

例如：

```text
SOP-A：轴承拆装
需要：
拿取
放置
扳手
轴承
螺栓

SOP-B：发动机部件拆装
需要：
拿取
放置
扳手
螺栓
零部件

SOP-C：电气接线
需要：
拿取
插入
万用表
导线
端子
```

那么“拿取”“扳手”“螺栓”都可以复用。

这才是真正降低新 SOP 上线成本的地方。

目前工业 AI-SOP 产品同样越来越强调把完整流程拆成“可观测、可校验的操作原子事件”，然后进行规则化时序判断，而不是让单一模型直接理解整个生产 SOP。

# 八、一个步骤应该包含哪些字段

建议把一个 SOP Step 至少拆成以下模型。

| 分类   | 字段                |
| ---- | ----------------- |
| 基本信息 | 步骤编号、名称、说明        |
| 流程属性 | 顺序、前置步骤、是否必做      |
| 教学内容 | 标准图片、标准视频、指导文字    |
| 识别条件 | 动作、工具、工件、区域、状态    |
| 时间规则 | 最短时间、最长时间         |
| 判定逻辑 | AND / OR、持续时长、置信度 |
| 异常规则 | 漏步、错序、错工具、超时      |
| 评分规则 | 标准分、各种异常扣分        |
| 能力映射 | 安全、规范、熟练度、工具使用等   |

比如：

```json
{
  "stepId": "S10",
  "name": "紧固端盖螺栓",

  "flow": {
    "required": true,
    "previous": ["S09"],
    "allowSkip": false
  },

  "recognition": {
    "logic": "AND",
    "conditions": [
      {
        "type": "OBJECT",
        "object": "torque_wrench"
      },
      {
        "type": "ACTION",
        "action": "tightening"
      },
      {
        "type": "TARGET",
        "target": "cover_bolt"
      }
    ]
  },

  "time": {
    "min": 2,
    "max": 30
  },

  "score": {
    "total": 5,
    "wrongTool": -2,
    "wrongOrder": -2,
    "missing": -5
  }
}
```

一期先不开放任意复杂逻辑表达式。

产品界面提供简单的：

```text
必须同时满足以下条件：

✓ 使用扭矩扳手
✓ 执行紧固动作
✓ 操作目标为端盖螺栓
```

底层再转成规则表达式。

# 九、SOP 状态机

每一个训练任务启动之后，系统实际运行的是一个状态机。

步骤状态建议统一定义为：

```text
WAITING
等待执行

READY
前置条件满足，可执行

IN_PROGRESS
正在执行

COMPLETED
正确完成

SKIPPED
跳过

FAILED
执行失败

TIMEOUT
超时

REVIEW_REQUIRED
AI无法确定，需要人工复核
```

假设标准顺序：

```text
S01 → S02 → S03 → S04
```

当前：

```text
S01 COMPLETED
S02 COMPLETED
S03 READY
S04 WAITING
```

这时系统检测到学生直接执行了 S04 对应事件。

系统不能只是：

> 识别到了 S04。

而应该判断：

```text
S04事件发生

↓

检查前置：
S03 != COMPLETED

↓

异常：
OUT_OF_ORDER

↓

记录：
学生提前执行S04

↓

根据当前模式决定：
训练模式 → 立即提示
考试模式 → 静默记录
```

这就是 SOP Engine 与普通动作识别系统之间最大的区别。

# 十、训练模式和考试模式必须从一期就分开

同一个 SOP，共享：

> 步骤、AI条件、评分规则。

但运行策略不同。

## 训练模式

核心目标是：

> 教会学生。

系统允许：

```text
显示当前步骤
显示标准操作
语音/文字提示
错误即时纠正
错误后允许重新执行
查看标准视频
完成后自动进入下一步
```

例如：

> 当前步骤：安装轴承  
> 检测到你正在使用错误工具。  
> 请重新选择规定工具。

训练模式下，“犯错”本身不是结束。

学生改正以后可以继续。

---

## 考试模式

核心目标变成：

> 客观记录和评价。

考试开始以后：

```text
不提示当前正确步骤
不告诉学生是否操作正确
不播放标准视频
不立即公布扣分
```

系统后台持续记录：

```text
10:01:23 S01 正确
10:01:46 S02 正确
10:02:07 S04 提前执行
10:02:16 S03 完成
10:03:22 S05 工具错误
……
```

考试结束：

> AI 自动形成建议成绩。

然后进入教师复核。

# 十二、教师端实时监控

教师面对的是一个班，而不是一个学生。

因此教师首页建议是“实训驾驶舱”。

例如一个班 24 个工位：

```text
工位01  张三   正常     06/11
工位02  李四   ⚠异常    04/11
工位03  王五   正常     07/11
工位04  赵六   已完成   11/11
……
```

教师点击工位 02：

```text
当前步骤：
S04 拆除端盖

最近异常：
10:22:31 错误工具
10:23:12 操作顺序错误

当前画面：
[实时视频]

[进入查看]
```

这里不要让教师不停盯着 24 个视频。

AI 的价值恰恰是：

> **把教师的注意力聚焦到异常工位。**

# 十三、自动评分体系

评分不能直接写死在算法里。

应该完全属于 SOP 配置。

例如：

| 步骤  | 分值  | 错误工具 | 错序  | 未完成 |
| --- | --- | ---- | --- | --- |
| S01 | 5   | —    | -2  | -5  |
| S02 | 5   | -2   | -2  | -5  |
| S03 | 10  | -3   | -5  | -10 |

同时增加一类特殊规则：

> **安全红线。**

例如：

```text
未佩戴护目镜
→ -10

设备运行状态下进入危险区域
→ 本项0分

严重违规操作
→ 考试终止
```

但“AI识别结果”不要直接修改最终成绩。

建议评分链：

```text
AI Event
↓
SOP判定
↓
生成异常
↓
评分规则
↓
AI建议成绩
↓
教师复核
↓
最终成绩
```

# 十四、教师复核中心

这是一期必须做，不应该放二期。

教师进入某学生成绩：

```text
张三

AI建议成绩：82
待复核异常：4项
```

打开：

```text
异常01

步骤：
S05 取下端盖

AI判定：
操作顺序错误

发生时间：
10:32:18

依据：
S04尚未完成

[播放 10:32:10 - 10:32:30]

AI置信度：
93%

处理：
○ AI判定正确
○ 修改为正常
○ 修改异常类型

教师备注：
____________
```

教师确认以后：

```text
AI建议成绩：82
教师调整：+2
最终成绩：84
```

必须保存：

```text
修改人
修改时间
原判断
新判断
修改原因
```

否则后期进入正式考试时缺乏可信度。

# 十五、视频证据链

建议从一期开始做到：

> **事件和视频时间轴完全绑定。**

一场训练形成：

```text
00:00 ───────────────────────── 08:42

     S01      S02   ⚠S03      S04
      │        │     │          │
      ▼        ▼     ▼          ▼
──────●────────●─────●──────────●────

                 ↑
              点击异常
```

点击 S03：

视频自动跳到：

```text
02:16
```

并播放前后例如：

```text
02:10 ～ 02:25
```

同时显示：

```text
标准：
使用扭矩扳手

实际：
使用普通扳手

判定：
工具错误

扣分：
-2
```

这一功能的价值远高于“保存完整录像”。

因为真正有教学价值的是：

> **结构化视频。**

而不是老师重新看 20 分钟录像。

学生训练结束后，一期报告不要做得太复杂。

```text
流程规范     82

操作熟练     78

```

一期不用做复杂 AI 诊断。

先把数据做对。

# 十七、能力画像的数据结构要提前做好

虽然一期只展示基础能力，但底层要支持：

```text
SOP Step
↓
Assessment Item
↓
Ability
```

例如：

```text
S10
紧固端盖螺栓

↓

工具选择
动作规范
操作结果

↓

工具使用能力
流程规范能力
装配技能
```

因此：

```text
一个Step
可以对应多个Assessment

一个Assessment
可以映射多个Ability
```

未来才能形成：

```text
学生个人画像
班级画像
课程画像
专业画像
```

否则后期只能统计成绩。

# 十八、AI Studio：一期只给内部技术人员使用

这个后台不要给教师。

一期技术人员至少需要管理：

| 模块  | 功能                    |
| --- | --------------------- |
| 数据  | 原始视频、样本片段             |
| 标注  | 工具、工件、动作、区域           |
| 数据集 | 训练集、验证集、测试集           |
| 模型  | 模型名称、版本               |
| 训练  | 训练任务、参数、日志            |
| 评估  | Precision、Recall、混淆情况 |
| 发布  | 测试→正式                 |
| 部署  | 哪些工位正在使用              |
| 监控  | 在线情况、推理状态             |

教师看到：

> 扭矩扳手识别。

AI工程师看到：

```text
tool_torque_wrench

detector:
tools_v3.1

action:
hand_object_interaction_v2.4

dataset:
ds_tool_20260912

precision:
0.96

recall:
0.93
```

这种分层非常关键。

# 十九、模型技术路线不要提前绑死 YOLO

一期当然完全可以大量使用 YOLO。

例如：

```text
工具识别
工件识别
PPE识别
```

YOLO 很合适。

但系统架构不能写成：

> YOLO识别系统。

更合理的是：

```text
目标检测
+
目标跟踪
+
人体关键点
+
人与物关系
+
动作时序
+
规则判断
```

某些动作甚至不需要专门训练“动作模型”。

例如：

> 拿取扳手。

可能只需要：

```text
手部关键点靠近扳手
↓
形成接触
↓
扳手位置开始跟随手部移动
↓
持续一定时间
↓
pickup_wrench
```

这是一个事件算法。

而不是必须训练一个：

> pickup_wrench 神经网络。

这能显著降低训练数据需求。

OTEK 当前公开的 AI-SOP 技术路线也采用了目标检测、姿态/关键点、动作基元和时序规则组合的架构，并指出固定视角、遮挡、反光和相似动作会显著影响真实场景效果。

# 二十、边缘部署架构

一期建议：

```text
                    学校服务器
                       │
         ┌─────────────┴─────────────┐
         │                           │
     教师电脑                     管理后台
         │
────────────────校园局域网────────────────
         │
     边缘推理节点
         │
   ┌─────┼─────┐
   │     │     │
 摄像头1 摄像头2 摄像头3
 工位01  工位02  工位03
```

是否真正做到“一工位一个边缘盒子”，一期可以根据成本测试决定。

不建议架构层强绑定：

> 一摄像头 = 一盒子。

产品应该支持：

> 一个边缘节点管理多个工位。

实际部署数量根据：

```text
视频路数
分辨率
FPS
模型大小
GPU/NPU性能
延迟要求
```

进行容量计算。

# 二十三、一期明确暂缓的功能

一期不要同时做 VR、数字孪生、LLM 自动生成 SOP、知识图谱、教师 AI 助手、复杂大模型动作理解、正式考试仲裁、跨学校资源共享、大赛系统、多专业全部覆盖、全自动标注和完全开放的无代码 AI 训练平台。

这些未来都可以讲故事。

但现在核心问题只有一个：

> **机器到底能不能稳定理解学生有没有按照 SOP 正确完成一系列真实操作。**

# 二十四、第一个 PoC 怎么选

第一个 PoC 不能由“哪个实训看起来高级”决定。

应该专门挑适合 AI 的项目。

理想项目特征是：

| 条件    | 要求     |
| ----- | ------ |
| SOP步骤 | 8～20步  |
| 工位    | 固定     |
| 摄像机   | 固定     |
| 学生人数  | 单人     |
| 工具    | 3～8种   |
| 工件    | 较明显    |
| 遮挡    | 较少     |
| 操作区域  | 明确     |
| 顺序    | 比较固定   |
| 结果    | 可观察    |
| 时间    | 5～15分钟 |

因此第一轮比较适合：

**螺栓/机械部件装配类实训。**

而不是一开始做高度精细、遮挡严重、自由度非常高的复杂机械维修。

难度适中，而且可以非常完整地测试：

> 工具识别、工件识别、动作识别、顺序判断、漏步、错工具、ROI、视频时间轴、自动评分。

# 二十六、PoC 验收指标不要只看“准确率”

建议验收分四个层级。

### 第一层：AI识别

例如：

```text
工具检测 Precision
工具检测 Recall
动作事件 Precision
动作事件 Recall
```

### 第二层：SOP判定

真正更关键：

```text
正确步骤识别率
漏步检出率
错序检出率
错误工具检出率
```

### 第三层：完整考试

随机让测试人员：

```text
正常操作
故意漏一步
交换两步
拿错工具
重复操作
执行一半后改正
```

最终判断：

> 系统给出的过程记录和教师人工记录一致程度。

### 第四层：复制能力

这是最重要的。

第一个 SOP 完成以后：

> 再换一个明显不同的 SOP。

记录：

```text
新增AI事件数量
复用AI事件数量
新增训练数据量
开发工时
配置工时
训练时间
最终上线时间
```

这才是真正检验“平台化”的指标。

# 二十七、一期成功的定义

我不建议把一期成功定义成：

> “做出了一个 AI 动作识别系统。”

而应该定义成：

> **至少完成两个真实实训 SOP。**

第一个 SOP 跑通完整产品闭环：

```text
SOP配置
→
AI事件配置
→
模型部署
→
学生训练
→
实时判定
→
错误纠正
→
考试
→
自动评分
→
教师复核
→
视频复盘
→
学生报告
```

第二个 SOP 则用来证明：

> 前面做出来的能力到底是不是可以复用。

只完成第一个：

> 证明技术可行。

成功完成第二个，而且接入成本明显下降：

> 才证明产品方向可行。

# 二十八、最终产品核心不是“算法”，而是三个资产

长期来看，真正会逐步形成壁垒的是：

**第一类：AI事件资产。**

例如：

```text
拿取
放置
拧紧
插入
测量
按压
……
```

以及：

```text
扳手
螺丝刀
万用表
游标卡尺
……
```

这些能力不断积累和复用。

**第二类：行业 SOP 资产。**

逐渐形成：

```text
机械
机电
汽修
电气
轨交
焊接
……
```

大量结构化标准 SOP。

**第三类：实训数据资产。**

包括：

```text
正确操作
错误操作
容易误判的操作
不同学生操作方式
不同光线
不同工位
不同遮挡
```

随着学校越多，模型才能真正越来越稳定。

# 二十九、最终产品形态

所以我建议以后对外不要讲：

> “我们使用 YOLO 对学生动作进行识别。”

这只是实现细节。

真正的产品表达应该是：

> **面向职业技能实训的 AI 智能指导与考评平台。**
>
> 系统通过 AI 视觉、设备数据和传感器，对学生真实实操过程进行实时感知，将操作行为与标准 SOP 自动比对，实现过程指导、错误纠偏、自动考评、视频复盘和学习分析，并通过可配置 SOP 引擎快速适配不同专业和实训项目。

而内部技术核心则是：

```text
AI Event Engine
       +
SOP State Machine
       +
Assessment Engine
```

如果这三块做扎实，未来不管接：

> 机械、机电、电气、汽修、轨交还是特种作业，

上层专业不同，底层都还是同一个产品。

---

# 三十、一期开工顺序

如果现在真正进入产品设计，我建议顺序不是先画所有后台页面，而是围绕核心链路推进：

**第一步先确定一个真实 PoC SOP并把教师评分表拿到手；第二步人工把 SOP 拆成“机器可判定事件”；第三步把 SOP Editor 设计出来；第四步定义统一 Event Schema 和 SOP 状态机；第五步再做 AI PoC；第六步做学生实时训练；第七步做视频时间轴和教师复核；最后再补教学管理、成绩和基础统计。**

原因很简单：

如果 **SOP Editor + Event Model + State Machine** 三件事成立，其他页面基本属于正常软件工程。

如果这三件事没定义清楚，再漂亮的教师后台最终也只是一个普通实训管理系统。

---

## 一句话总结一期

**一期不是要证明 AI 能“看懂所有实训”，而是要证明：我们能把一个老师脑中的标准操作规程，系统化地翻译成机器可感知、可判断、可评分、可复核的数字 SOP，并且这套机制能够快速复制到第二个实训项目。**

这应该作为后续整个产品设计、技术选型和项目验收的最高原则。
