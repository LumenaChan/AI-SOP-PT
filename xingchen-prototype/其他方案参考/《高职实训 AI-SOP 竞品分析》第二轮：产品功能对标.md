# 二、一个 SOP 步骤到底应该配置什么

我现在建议我们把“步骤”设计成真正的**事件判定节点**，而不是一句说明文字。

例如：

### S07：紧固 A 点螺栓

教师看到的配置界面应该可以设置：

```
步骤名称：紧固A点螺栓

执行顺序：第7步
步骤性质：必做
前置步骤：S06

识别条件：
☑ 操作者进入装配区域A
☑ 使用工具：扭矩扳手
☑ 目标物：A点螺栓
☑ 识别动作：紧固
☑ 扭矩值：30～35 N·m

通过逻辑：
视觉条件全部满足
AND
扭矩传感器 ≥ 30 N·m

异常规则：
□ 错误工具
□ 错误位置
□ 提前执行
□ 未执行
□ 超时

标准分：5
错误工具：-2
顺序错误：-2
未完成：-5
```

这才是真正的 SOP 引擎。

最后组合成不同 SOP。

# 四、这一点会直接决定产品能不能规模化

假设现在有三个专业：

```
机电专业
SOP A：
拿万用表 → 测电压 → 接PLC

汽修专业
SOP B：
拿扭矩扳手 → 定位螺栓 → 紧固

机械专业
SOP C：
拿游标卡尺 → 测量工件 → 记录结果
```

传统项目制方式会变成：

```
模型A
模型B
模型C
```

三个专业各搞一套。

我更建议：

```
【通用动作库】
拿取
放置
插入
拔出
紧固
测量
按压
旋转
……

+

【对象模型库】
万用表
PLC
扭矩扳手
螺栓
游标卡尺
工件
……

+

【关系事件】
人拿工具
工具接触对象
手进入区域
物体进入区域
设备状态变化
……

↓

SOP规则编排
```

于是不同专业只是在**重新组合能力**。

这和轻象公开强调的“动作序列快速定义”思路是一致的。它同时把 ActionStudio 定义为动作 AI 的低代码开发 IDE，并将视频自动结构化成 SOP 标签、动作标签、时间标签、产品 ID 等数据。

# 六、我建议产品从一开始就设计两种运行模式

### 训练模式

系统可以告诉学生：

> 当前第 5 步。  
> 请使用扭矩扳手。  
> 检测到你拿取了普通扳手。  
> 工具错误，请重新选择。

甚至可以播放标准视频。

### 考试模式

则应该：

> 不提示。

系统静默记录：

```
00:32  S01 正确
00:48  S02 正确
01:06  S04 提前执行
01:09  S03 漏做
01:24  S05 工具错误
……
```

考试结束以后统一评分。

这个功能虽然看起来很小，但实际上关系到整个产品逻辑：

**同一个 SOP，不同运行策略。**

所以 SOP 不要直接绑定“是否提醒”。

应该配置：

```
SOP
├── 训练策略
├── 考试策略
└── 比赛策略
```

# 八、视频证据链：我现在认为一期就应该做

之前如果做 MVP，我可能会把“视频复核”放晚一点。

现在看完竞品后，我会把它提前到一期。

原因很简单。

学生问：

> “老师，我哪里做错了？”

老师不能看到：

> 第8步错误。

而应该能直接点击：

> **第8步错误 → 01:32–01:39 视频**

画面里同时显示：

```
AI判断：
应使用：扭矩扳手
实际识别：普通开口扳手

模型置信度：94%

规则：
S08.tool == torque_wrench

判定：
工具错误
扣2分
```

这同时解决三个问题：

**教学复盘、教师纠错、AI误判处理。**

宝华特别强调原始多机位视频保留用于复盘和争议复核；轻象把作业视频自动切片并形成 SOP、动作、时间等结构化标签；合米则强调每一步操作留痕和全链路追溯。

# 十五、我们的一期到底应该做哪些

经过这两轮竞品研究，我现在会把一期严格压缩成 **8 个核心系统模块**：

2. **基础教学管理**：专业、课程、班级、学生、教师、实训项目、任务。

3. **SOP Editor**：步骤、顺序、必做项、识别事件、标准视频、时间、异常规则、评分规则。

4. **AI事件库**：工具、工件、人体动作、ROI区域、人与物关系、对象状态。

5. **实时实训引擎**：当前步骤识别、完成判断、漏步、错序、错工具、超时、安全违规。

6. **训练/考试双模式**：训练实时纠错；考试静默记录和自动评分。

7. **考评系统**：AI建议分、教师复核、最终成绩、评分依据。

8. **视频证据链**：全程录像、步骤时间轴、异常片段、AI判定结果、标准操作对比。

9. **基础学情分析**：个人成绩、错误类型、步骤错误率、班级高频错误。

这里我暂时**不建议一期做**：

复杂工作流、完全自动 SOP 生成、多专业通用动作大模型、复杂数字孪生、VR、知识图谱、大模型教师助手、自动课程生成、跨校资源共享平台、复杂能力画像以及正式考试仲裁系统。

那些很容易把 MVP 拖死。

# 十九、现在回头看我们之前的技术方案，我会改一个很重要的地方

之前我们的思路比较像：

> 海量视频 → YOLO训练 → 建立标准SOP → 摄像头实时识别学生 → 对比SOP。

现在我会修改成：

> **先定义 SOP 的“可机器判定事件”，然后决定每一种事件由什么技术识别。**

顺序应该是：

```
真实教学SOP
        ↓
SOP步骤拆解
        ↓
每一步拆成可观察事件
        ↓
决定感知方式
 ┌────────┬────────┬────────┐
视觉      语音      PLC      传感器
 ↓         ↓         ↓         ↓
AI事件标准化
        ↓
SOP状态机
        ↓
评分/纠错
```

也就是说：

### 不应该先问

> “YOLO能识别哪些动作？”

而应该先问：

> “老师判定这个步骤是否完成时，究竟依据什么？”

如果老师判断：

> “学生必须使用扭矩扳手并达到 35N·m。”

那么机器条件就是：

```
视觉：
tool = torque_wrench
action = tightening
region = bolt_A

传感器：
torque >= 35
```

这就把**教学规则翻译成机器规则**了。

我认为这是目前整套产品最关键的一层抽象。
